## 一、设计目标

用户提了五件事，本文按"新建筑 + 一条新机制 + 一次面板重构"来组织：

1. **市场**：周期刷新的买/卖挂单，用来**补充稀缺物资**和**把余货换成金币**
2. **研究所改成默认建筑**：建了研究所才能研究（科技树少一项）
3. **仓库要能被认出来**：世界里的仓库建筑缺少"仓库"名字标签（已定位为 bug）
4. **城镇中心**：默认建筑，村民与市政信息的载体；右侧常驻面板取消，改为"点建筑才出面板"
5. **仓储上限**：物资有上限，超了**所有物资按同一比例削减**（不是"先丢便宜的"，见 §3.3）；
   上限由城镇中心 + 仓库提供，仓库可升级、每座要一个工人

一句话概括新增的经济张力：

> **以前是"缺钱"，现在还要"缺地方"。** 产量上来之后，如果不同步扩建仓库，
> 多出来的东西会直接烂掉 —— 这给了"扩产"和"扩仓"一个真实的取舍。

## 二、城镇中心（新建筑）

> **本节已按用户拍板定稿**："对这是村庄起始建筑，原先是仓库，按照新设计这个其实就是城镇中心。
> 仓库以后会是可以建的建筑。"
>
> 所以：**世界正中那座硬编码建筑就是城镇中心**（它现在被错误地叫成"仓库"），
> 仓库则是**另一座、以后可以建的**内容建筑（§四）。本节把「需求 4 城镇中心」
> 和「需求 3 仓库没名字」合并写 —— 它们本来就是同一件事。

### 2.1 定位

城镇中心是**村子的核心**，也是**唯一开局就有的建筑**。它承担四件事：

1. **一点点仓储**（§三的上限来源之一）
2. **市政信息的载体**：点它才显示人口 / 就业 / 满意度 / 国库 / 移民 / 日志（§七）
3. 世界层的视觉地标
4. **村民的空间锚点**：兜底住房 + 上班时的搬运目的地 + 展示村庄的布局基准
   （这三件事现在挂在硬编码仓库身上，见 §2.4）

### 2.5 为什么"仓库"三个字没画出来 —— 真因（**已定位到语句顺序，不是猜测**）

用户报的是："仓库的建筑上没有仓库两个字"。**核实结论：用户是对的。**
而且按 §2.3 它以后要改成「城镇中心」，正好一并修。

#### 第一步：证明"是哪一座"（不靠"中间那栋大的看着像"）

坐标验算（`W = H = 512`、`TILE = 16`；截图 1600×900，`screenshot.gd` 把 zoom 设成 2.0）：

```
map.center       = (256, 256)                              game_map.gd:29
map.warehouse    = Rect2i(254, 255, 4, 3)                  game_map.gd:33
                   → 中心 = (254+2, 255+1.5) = (256, 256.5)
camera.position  = center × 16 = (4096, 4096)              world_view.gd:370
屏幕坐标 = (world − cam) × zoom + 视口/2
仓库中心 = ((4096, 4104) − (4096, 4096)) × 2 + (800, 450) = (800, 466)
它应有的标签锚点 = (800, 450)                              _add_label 的 cx / roof_cy 算法
```

对照实测截图：**那座没有名字标签的大建筑正好落在 (800, 466)**，
而 (800, 450) —— 标签本该出现的位置 —— 是空白。→ 就是它。

#### 第二步：真因 —— **不是"只加过一次标签"，而是"加了之后又被清掉"**

这是本次排查的结论，**可以指到具体两行**：

```gdscript
# world_view.gd
623: func showcase_village(seed_value: int) -> void:
624:     start_new_game(seed_value, 10.0, "sovit")   # ← 内部 :773 rerender → :777 _build_warehouse() → 标签「加上了」
...
633:     _lay_showcase_ground()                      # ← 内部 :752 _rerender_terrain() → :518 _clear_labels() → 标签「被删了」
```

- `_lay_showcase_ground()`（`:729`）**最后一行**就是 `_rerender_terrain()`（`:752`）
- `_rerender_terrain()` 的**第一行**就是 `_clear_labels()`（`:518`）
- `_clear_labels()` 会把 `_label_items` 里的**所有**标签 `queue_free` 并清空（`:164-169`）
- 之后**再没有任何地方重建仓库标签** —— `_build_warehouse()` 只在
  `:99`（`_ready`）、`:777`（`start_new_game`）、`:826`（`load_from`）三处被调用，
  而 `showcase_village()` 里那次 `_lay_showcase_ground()` 排在 `start_new_game()` **之后**

**所以这是一个纯粹的语句顺序 bug**：同一函数里"先建（加标签）、后铺地（清标签）"。

#### 第三步：各条路径的结论（**用户正式开局时标签是在的**）

| 路径 | `_clear_labels()` 之后有没有再建仓库 | 标签 |
|---|---|---|
| 标题页展示村庄 `showcase_village()`（`:623`） | ❌ 没有 | **丢** ← 截图复现的就是这条 |
| 正式开局 `new_game_dialog.gd:119 → world.start_new_game()` | ✅ `:773` 清 → `:777` 建 | 在 |
| 读档 `load_from()` | ✅ `:811` 清 → `:826` 建 | 在 |

也就是说：**只要玩家从标题页直接"开始游戏"，标签是会出现的**。
但下面两种情况会看到没标签的仓库：

1. **在标题页停下**（`main.gd:157 _title.begin_showcase()` 已经把展示村庄铺好了，
   而 `_end_title()`（`main.gd:160`）**只隐藏标题层、不重开一局**）——
   用户很可能就是在这里看到的
2. 任何"先 `_build_warehouse()` 再 `_rerender_terrain()`"的未来调用顺序

> `_end_title()` 的注释原文就是："标题页结束：露出游戏 UI（展示用的那局已被新游戏/读档覆盖）"
> —— 它假定调用方随后会开新局或读档。

#### 第四步：修法（进【待改动清单】，本文不动代码）

- **A（推荐，治本）**：在 `_rerender_terrain()` 的 `_clear_labels()` 之后，
  **统一补回城镇中心的标签** —— 即把它纳入"重画地形后要重建的标签清单"，
  和商店（`:515`）/ 住房（`:476` / `:963`）享受同一条路。
  这样**任何**调用顺序都不会丢
- B：把 `showcase_village()` 里的 `_lay_showcase_ground()` 挪到 `start_new_game()` **之前**
  —— 治标：只修好这一条路径，将来新加的调用点还会复发
- C：在 `_clear_labels()` 里跳过城镇中心那个标签 —— 同样是治标，而且让"清空"语义变得不干净

**推荐 A**，并且它和 §2.3 的改名是同一批改动，一起做最省事。

## 三、仓储上限

### 3.1 口径：全局总量（推荐）

**上限 = 所有物资的总和**，而不是"每种物资各自一个上限"。

| | 全局总量（推荐） | 每种商品一个上限 |
|---|---|---|
| 玩家心智 | 「仓储 840 / 2000」一个数 | 36 个数字 |
| 仓库加成 | 每座 +300，简单 | "+300" 是加在哪几种上？ |
| 副作用 | 囤石头会挤掉面包的位置 | 无 |
| 取舍感 | **强**（逼你把货用掉/卖掉） | 弱 |

选全局总量。副作用（囤积一种货挤占其它）**正是这个机制想要的张力** —— 用户的原话是
"超过了就放不下就丢掉了浪费了"，就是要让玩家感到"地方不够"。

⚠️ 2026-10 补充：**"挤掉"是同比例的，不是"把便宜的丢光"**。见 §3.3。

**计入范围**：`state.goods` 里的**全部**商品（含易腐的蔬菜/肉类/鱼类）。

> 易腐品当晚就会被损耗掉，不会长期占位；把它们排除反而要多一条特例，
> 且会出现"界面显示 X 但实际不占地方"的困惑。保持"所见即所占"。

### 3.2 数值

| 来源 | 容量 | 条件 |
|---|---|---|
| **城镇中心** | **+2000** | 开局就有 |
| **每座仓库（1 级）** | **+300** | **需要 ≥1 名在岗工人**（用户要求"每个仓库目前需要有一个工人"） |
| 仓库升级每级 | **+150** | 2 级 +450、3 级 +600…… |

推导：

- v0.3 开局 12 人全是穷人 → 日耗 `coarse_bread 1.0 + vegetable 0.5` = **18 单位/日**
  （来源 `content/classes.json` 的 `poor.needs`）
- 城镇中心的 2000 ≈ **111 天**的纯口粮（12 人 × 1.5/天 = 18/天），
  也正好是"只靠城镇中心能撑到多少人口"的上限（≈150 人，推导见 §4.2）
- **为什么从 1000 提到 2000**（2026-10，用户拍板）：开局有资源倍率
  （简单 ×2 / 普通 ×1 / 困难 ×0.5，见 `new_game_dialog.gd`），v0.3 的 ×1 开局物资合计
  **980**，×2 就是 **1960** —— 1000 的容量在"简单"档**第一晚就爆仓**。提到 2000 之后
  ×2 开局刚好装得下，玩家有几天缓冲去建第一座仓库。
  （用户原话："城镇中心存储太少了初始 2000 吧。"）
- 一座仓库 +300 ≈ **再 17 天**口粮 / 再多养 25 人 —— 玩家会想建，但不至于开局就必须建
- 仓库成本定得低（`{wood 8, stone 6}` / 36 建造力 / 1 工人），因为它是**基础设施**
  而不是奢侈品；卡它的是"工人"和"位置"

### 3.3 丢弃规则

**时机**：夜晚结算，**紧接 `applySpoilage` 之后**（`src/engine/tick.ts:104`）。

现有夜晚顺序（`tick.ts:87-107`）：

```
settleConstruction → settleResearch → payWages → assignTenure → collectRent
→ runConsumption → runPrivateHousingMarket → assignTenure → updateSatisfaction
→ updatePopulation → applyAdmission → applySpoilage → ✱ 新：applyStorageCap
→ growSkills → computeArrivals → reserved={} → history
```

放这里的三条理由：

1. **一天只判一次**，与损耗同一节奏
2. **在施工结算之后** —— 开工扣材料发生在**当天第一个工作小时（06:00）**，
   比入夜的"超限丢弃"（`applyStorageCap`，§2.4）早，不会被抢走材料
3. **在 `applySpoilage` 之后** —— 先损耗、后判上限；损耗腾出的空间可以救下本来会被丢的货

**削减规则（确定性，2026-10 改）**：**所有物资按同一比例削减** ——
`keep = 容量 / 总量`，每种物资保留 `floor2(原值 × keep)`（向下取整到 2 位小数）。
一天只写一条 `log`：「仓储超限（2040 / 2000）：所有物资按 98.04% 削减，共丢弃 40 单位」。

改成同比例的三条理由：

1. **旧规则会先杀掉食物**。原来是"按 `baseValue` 升序丢（先丢便宜的）"，而食物恰好是
   最便宜的（小麦 1.0 / 蔬菜 1.2 / 粗面包 1.3 / 木材 1.5 / 石块 1.6）——
   于是超限时**蔬菜和面包第一个被丢光**，仓库里剩下的全是建材。
2. **实测后果是灭村**。开局选"简单（资源 ×2）"：物资 1960 > 容量 1000，第一晚丢
   `300 粘土 + 174.6 蔬菜 + 388 粗面包 + 60 木材`，村里一点吃的都不剩，
   12 人 → 4 人。这是用户实际报上来的 bug。
3. **同比例没有"谁该先死"的判断成本**。玩家想保护某一种货，用 §3.6 的逐项软上限
   显式表达（那才是"我就是要先削木材"的正确出口），而不是靠一个隐式的价格排序。

> 向下取整（而不是四舍五入）是为了让不变量好写：**削减后总量一定 ≤ 容量**，
> 代价是每种货最多多丢 0.005。TS 与 GDScript 都用 `floor`，逐位一致。

**`reserved` 不额外计算**：`reserved` 是"今日已计划消耗"的占位标记，不是第二份库存
（`docs/spec.md` §2.1）。上限只按 `state.goods` 的现值算。

**日志 / 提示**：每次丢弃写一条 `log`（"仓储超限，丢弃 X 单位 Y"）并置一个 `alert`
（类型 `storage_full`），否则货凭空消失，玩家会以为是 bug。

### 3.4 与其它机制的交互

| 机制 | 交互 |
|---|---|
| **在建工程材料** | `settleConstruction` 开工时先从 `goods` 扣材料，**发生在丢弃判定之前** → 不会出现"因为超限把工地材料丢了导致工地卡死" |
| **市场买入** | **买入前必须检查余量**：`当前总和 + 购入量 > 上限` 时**拒绝交易**并提示"仓储不足"。否则刚买的货当晚被丢掉，体验极差 |
| **市场挂单（卖出位）** | 未成交的挂单**不占仓储**（它只是报价）；挂单刷新时直接作废 |
| **生产** | 白天生产直接累加进 `goods`，**允许白天短暂超出上限**，夜晚才结算 —— 上限是"日终规则"，符合直觉 |
| **易腐 `perishRate`** | 先损耗再判上限（§3.3） |
| **`buildCost` 退款（拆除）** | 拆除退材料时如果会超上限，**按余量退**（超出的部分变成"丢弃"）或直接退到上限为止 —— 实装时按后者，简单 |

### 3.5 ✅ 开局物资：**不用砍了**（2026-10 复核）

> 这一节原是"⚠️ 必须同时改 v0.3 的开局物资"，理由是"开局物资合计 1060，
> 略超 1000 的上限 → 第一天会丢 60"。**那两个前提现在都不成立**：
> 上限已提到 **2000**，而且实测的开局物资是 **980**（不是 1060）。

v0.3 现在开局物资合计 **980**（`coarse_bread 200 / wood 300 / stone 150 / clay 150 /
vegetable 100 / firewood 40 / brick 40`），**远低于 2000 的上限** → 第一天什么都不丢。

下面那张"砍到 340"的旧建议**作废**（保留在此仅作历史记录）：
它的依据是"没有上限时代的安全垫"与"上限 1000"两条，两条都过期了。

| 商品 | 旧值 | 旧建议 | 现状 |
|---|---|---|---|
| `coarse_bread` | 200 | 120 | **保持 200**（≈16 天口粮） |
| `vegetable` | 100 | 60 | **保持 100** |
| `wood` | 300 | 80 | **保持 300** |
| `stone` | 150 | 40 | **保持 150** |
| `clay` | 150 | 20 | **保持 150** |
| `firewood` | 40 | 20 | **保持 40** |
| `brick` | 40 | 0 | **保持 40** |
| 合计 | **980** | 340 | **980 / 2000 = 49%** |

**开局建得起仓库吗？**（这是"石作赶不赶得上"那条风险的正面回答）

| 项 | 木材 | 石块 | 砖 |
|---|---|---|---|
| 研究所 | 12 | 0 | 0 |
| 伐木场 | 4 | 0 | 0 |
| 采石场 | 4 | 0 | 0 |
| 小麦农场 | 4 | 0 | 0 |
| 蔬菜农场 | 4 | 0 | 0 |
| 建筑工坊 | 6 | 4 | 0 |
| **仓库（第一座）** | **8** | **6** | **0** |
| **合计** | **42** | **10** | **0** |
| v0.3 开局库存 | 300 | 150 | 80 |
| 结论 | 余 258 ✅ | 余 140 ✅ | 不用砖 ✅ |

→ **开局第一天就建得起仓库**（石块只要 **6**，开局有 **150**，是需求的 15 倍），
**完全不需要先研究「石作」**。所以"仓库建不起"这条风险**不成立**，
**不建议提高开局石头** —— 现状 150 就已经是"给够了石头"。
仓库要的也不是砖（`{wood 8, stone 6}`，不含 `brick`），开局那 40 砖与它无关。

`v1.0` 开局物资合计 **120**，远低于 2000，**不用改**。

> 开局物资**没有**被改动，所以 golden 轨迹不因它漂移（§九的漂移说明现在是历史记录）。

### 3.6 每种物资的软上限（用户补充的需求，**已实装**）

> 用户原话："资源可以设置每一项资源的上限，这是人为设置的软上限
> （防止某一个物资太多导致其它物资无法收获）。"

全局总量口径有一个副作用：**一种货囤满了，别的物资生产出来就收不下、当晚被削减**。
逐项软上限就是给玩家一把刀，把那一种货先削掉，剩下的空间留给别人
（同比例削减下它的意义更明确：**不设上限，面包也会跟着一起缩水**）。

**口径**

| 项 | 值 |
|---|---|
| 存放位置 | `state.government.storageCaps`（`{goodId: 上限}`，缺项 = 该项不限） |
| 默认 | **空表 = 全部不限**（不设就退化成 §3.1 的纯全局口径） |
| 设置方式 | 命令 `set_storage_caps { caps }`（**整体替换**；只收本 pack 存在的商品；非负整数；`0` 视为不限、不入表） |
| UI | **选中仓库**（点地图上的仓库）→ 弹出**浮动对话框**的「资源（数量 / 上限）」：每种资源一格，左边是当前数量、右边是上限输入框，**留空 = 不限**；同时显示「全村仓储 已用 / 上限」。⚠️ 2026-10 从「设置资源」面板搬过来的 —— 那里原本和"顶栏显示哪几种资源"混在一起，两件事都不清楚 |
| 生效时机 | 与全局上限同一处：**日终结算、紧接损耗之后**（§3.3） |
| 执行顺序 | **先按逐项上限修剪，再判全局总量** |

**为什么必须先逐项、后全局**：先修剪单项 = 让"被限额的那种货"先退出占用，
剩下的空间留给别人；反过来的话，全局那一刀先按比例把所有货（包括刚出炉的口粮）
都削一遍，逐项上限再修剪就已经没意义了。

**日志**：逐项上限丢弃按商品 id 顺序遍历（确定性），每种写一条
`log`（`kind = 'storage'`，文案「X 超过单项上限 N，丢弃 M 单位」）；
全局那一步只写**一条**汇总（"所有物资按 xx% 削减"），因为它是"一起缩水"，
逐种写会把公告栏刷满。

**为什么不做成"超过就不产"**：产线是否开工由排产（§2.1）决定，和"仓库存不存得下"是两件事；
而且"产了又丢"本身就是给玩家的信号 —— 该去调上限、或者该把人从那条产线上撤下来了。

### 4.2 仓储上限的成长曲线（**推导，不是拍脑袋**）

先定"**要装多少**"，再看"**该给多少**"。所有输入都从 `content/*.json` 实算。

#### 输入（实算值）

| 量 | 值 | 来源 |
|---|---|---|
| 穷人日耗 | **1.5 单位/人·天** | `classes.json`：粗面包 1.0 + 蔬菜 0.5 |
| 中产日耗 | 0.88 单位/人·天 | 白面包 .5 + 肉类 .2 + 粗布衣 .05 + 陶器 .03 + 娱乐 .1 |
| 富人 / 老板日耗 | 1.15 / 1.6 单位/人·天 | 同上 |
| **开局粮食链满员日产出** | **36 单位/天** | 粗面包房 2 人 → 24 粗面包/天；蔬菜农场 4 人 → 12 蔬菜/天 |
| 开局 12 人日耗 | **18 单位/天** | 1.5 × 12 |
| 伐木场 / 采石场 / 粘土坑满员 | 10 / 8 / 8 单位/天 | `buildings.json` 的 recipe |
| 砖窑满员 | 6 砖/天（另耗 4 木柴） | 同上 |
| 最贵的单座建筑料 | 市场 `{wood 20, stone 10, brick 10}` = **40 单位** | §5.1 |

#### 两条关键结论

**① 食物链天生净过剩 → 库存必然涨到触顶。**

```
满员产出 36/天  −  12 人日耗 18/天  =  净 +18/天
```

所以仓储上限不是"极限情况"才碰到，而是**开局几天后就会天天碰到**。
触顶之后玩家只有三条路：

1. **建仓库**（+300）
2. **调低开岗数**（少产；`inspector` 的用工滑块拖到 0 就是停产）
3. **卖给市场**（需要「商贸」科技，era 2，见 §5）

**这正是这个机制想要的取舍。** 没有上限时，玩家会无脑把每条产线拉满；
有了上限，"产多少"第一次变成一个需要想的决定。

**② 触顶时间可以算**：`(上限 − 开局物资) / 净结余`。
开局物资 980（§3.5）、城镇中心 2000 → 余量 1020 → **约 57 天触顶**。

#### 所需上限的经验式

```
所需上限 ≈ 8 天的口粮 + 一次施工队列(4 项)的料
        = 8 × 1.5 × 人口 + 4 × 40
        = 12 × 人口 + 160
```

- **8 天的口粮**：够撑过一次收成波动、或一次改产线的过渡期
- **4 项施工队列的料**：`docs/construction.md` 记录的 AI 施工队列上限是 4 项

#### 供给与阶段对照

```
供给 = 2000（城镇中心）
     + 300 × 仓库数
     + 150 × 已升级总级数
```

| 阶段 | 人口 | 所需 = 12×人口+160 | 供给 | 结论 |
|---|---|---|---|---|
| 开局 | 12 | 304 | **2000** | 余 1696 ✓ |
| 中期 | 50 | 760 | 2000 | 余 1240 ✓ |
| 中后期 | 100 | 1360 | 2000 | 余 640 ✓ |
| 后期 | 150 | 1960 | 2000 | 余 40，**该建仓库了** |
| **只靠城镇中心的上限** | **~153** | 1996 | 2000 | **城镇中心一个人能撑到约 150 人** |
| 首次触顶后 | 160 | 2080 | 2000 ✗ → 建 1 座 → **2300** | 必须建仓库 |
| 大后期 | 200 | 2560 | 2300 | 略紧 → 2 座 = 2600 |

**两条好记的规律**：

- **城镇中心能撑到约 150 人**（`(2000 − 160) / 12 ≈ 153`）
- **之后每多 25 人口，需要多一座仓库**（`300 / 12 = 25`）

> 2026-10：城镇中心从 1000 提到 2000，上表与两条规律都是按 2000 重算的。
> 原先"城镇中心能撑到约 70 人"是 1000 时代的值。

#### 中期会不会卡死？不会，但会"紧"

人口 160 时 1 座仓库 = 2300，所需 2080 —— 只剩 220 余量。如果玩家同时囤建材盖剧院
（一次 4 项 × 40 = 160 单位），就几乎顶到上限。

这时有**两种扩张方式**，各有适用面 —— 这正是"仓库可升级"的意义：

| 方式 | 花费 | 收益 | 适合 |
|---|---|---|---|
| **新建一座仓库** | 36 建造力 + `{wood 8, stone 6}` + **1 个工人** | +300 | 人手宽裕时 |
| **升级现有仓库** | `24 × 当前等级` 建造力（**不占新地皮、不加工人**） | +150 | 人手紧张时 |

#### 开局物资：已经不用动了

见 §3.5 —— 开局物资实测 980，上限 2000，**占 49%**，第一天什么都不丢。
（旧稿写的"砍到 340"是上限 1000 时代的事，已作废。）

> ✅ **原稿那条平衡风险已排除 —— 但原因不是"上限调高了"。**
> 原稿担心"触顶时还没研究出「石作」→ 建仓库的石块可能还没有"，这个判断
> **从一开始就站不住**：v0.3 开局库存本来就有 **150 石块**，而建一座仓库只要
> **`{wood 8, stone 6}`**（开局那批必需建筑加起来也只要 10 石块，核对表见 §3.5）。
> **仓库第一天就建得起，不需要「石作」。** 所以触顶从来不是死路 ——
> 这与城镇中心是 500 / 1000 / 2000 无关。
> 真正的约束只是**工人**与**地皮**（仓库要 1 个在岗工人）。

### 4.3 开局不给仓库

用户拍板"仓库以后是可以建的建筑"，且需求 4 说"**默认只有城镇中心**"。
所以：

- `v0.3.start.shops`：`{}` → `{ "town_center": 1 }`，**不加** `warehouse`
- `v1.0.start.shops`：加 `town_center: 1`（+ `research_institute: 1`，见 §6.6），
  同样**不加** `warehouse`

（前一稿曾建议 v0.3 预置一座仓库，现已作废。）

### 5.3 刷新节奏与确定性（**这条决定 golden 能不能过**）

**刷新时点**：黎明，`(day - 1) % 7 == 0` → **第 1、8、15、22、29… 天**。
（即开局第一天就有挂单，之后每 7 天一次）

**随机来源：同存档随机，且不碰主 `rng` 游标。**

项目现在只有一个 rng 游标 `state.rngState`，它被人口/消费等系统共用。
如果市场也从这条流里抽数，那么**"建了市场"这件事本身会改变人口走向**——
这既难推理也难对拍。

所以市场用**独立的派生流**：

```
refreshIndex = (day - 1) / 7            // 0, 1, 2, …
streamSeed   = (state.seed * 2654435761 + refreshIndex) >>> 0     // Knuth 乘子，取 32 位
rng          = createRng(streamSeed)    // 就是现成的 mulberry32（docs/spec.md §13）
```

这条式子满足用户的要求"每个存档同一个种子"：

- **只依赖 `state.seed` 与 `refreshIndex`** → 同一个存档、同一天，反复进游戏结果完全一致
- **没有游标要存** → 存档/读档不需要额外字段，也不会因为"读档后多抽了一次"而分叉
- **完全不推进 `state.rngState`** → 不干扰人口/消费，`golden` 的既有轨迹不会因为
  "代码里多了一个 rng 消费者"而漂移

**抽取顺序（必须精确到第几次，TS 与 GDScript 要对齐）**：

```
pool = pack.goods 过滤"产出它的建筑此刻已解锁" → 按 goodId 升序排序
for side in [出售侧(市场卖给你), 收购侧(市场从你买)]:      # 固定顺序，先卖后买
    cand = pool 的副本
    for i in 0..3:
        k = floor(rng() * cand.size())
        slot[side][i].goodId = cand[k] ; cand.remove(k)
    for i in 0..3:
        slot[side][i].spread = rng()                       # 见 §5.4 的价格公式
        slot[side][i].qty    = 该侧的固定公式（§5.5）
```

**每次刷新固定 8 次选取 + 8 次 `spread`，共 16 次 `rng()`**。
`qty` 是算出来的，不抽随机 → 少一个自由度，少一处可能分叉的地方。

> `rng` 只在"存在至少一座已建成的市场"且命中断言时点时才创建并抽取。
> 没有市场的存档根本不碰这条流。

### 5.4 价格（买、卖**都高于**基准价，且浮动）

用户要求："购买/出售都比正常价格高，你要浮动一下"。

设 `base = ALL_GOODS[gid].baseValue`，`s = spread ∈ [0,1]`（§5.3 每格抽一个）：

| 方向 | 公式 | 取值范围 |
|---|---|---|
| **市场卖给你**（你要花金币） | `p_sell = base × (1.25 + 0.25 s)` | **1.25 ~ 1.50 × base** |
| **市场从你买**（你收金币） | `p_buy = base × (1.05 + 0.15 s)` | **1.05 ~ 1.20 × base** |

两者都严格高于 `baseValue` ✓ 符合用户要求。

**价差是刻意的**：`1.05 + 0.15s ≤ 1.20 < 1.25 ≤ 1.25 + 0.25s`
→ **同一次刷新内，"从市场买进再卖回市场"必定亏钱**（最少亏 5% 价差）。
这条不等式是防套利的地基，实装时必须写进断言（见 §5.6）。

### 5.5 数量

| 侧 | 公式 | 12 人时 |
|---|---|---|
| 出售侧（卖给你） | `qty = max(2, round(pop × 0.25))` | **3** |
| 收购侧（从你买） | `qty = max(3, round(pop × 0.4))` | **5** |

随人口增长，挂单量也跟着涨（村子越大，贸易越有份量），但**增长慢于人口**，
避免后期"靠市场就能养活全村"。

### 5.6 ⚠️ 套利风险分析（**必须看这一段**）

用户要求"买卖都比正常价格高"。这个要求本身**带一个印钞漏洞**，我先把账算清楚。

**风险 1：市场内双向对冲 —— 已被价差堵死**

`p_buy_max = 1.20 × base` 严格小于 `p_sell_min = 1.25 × base`。
> 买 1 单位再卖回去，至少亏 `0.05 × base`。**不可能通过市场自身套利。**

**风险 2：跨刷新套利 —— 同样被堵死**

`p_sell` 的最低值（1.25×）仍高于 `p_buy` 的最高值（1.20×），
所以"在 A 次刷新买入、在 N 次刷新后卖出"也必亏。

**风险 3：把自产货卖给市场 = 真实的金币来源（这是设计意图，不是漏洞）**

市场**从你手里买**的价格高于基准价，而村民在你店里买东西是按 `state.prices`
（默认 = `baseValue`，见 `src/engine/state.ts:37`；只有玩家用 `set_price` 动作改它，
`src/engine/actions.ts:90`）。所以：

- 卖给市场 ≈ `1.05~1.20 × base`
- 卖给村民 ≈ `1.0 × base`（默认价）

→ 玩家有动机把货卖给市场。**规模测算**（12 人、`base≈2`）：

```
收购侧 4 格 × 5 单位 = 20 单位 / 7 天
按均值 1.10 × base = 2.2 计 → 44 金币 / 7 天 ≈ 6.3 金币/天
```

对比同期现金流出：12 人 × `refWage 3` = **36 金币/天**（`src/engine/systems/finance.ts`）。
**市场只回补约 17%**，不会失控。

反向（玩家从市场买）是**纯金币销毁**，正是这个游戏需要的货币回收：

```
出售侧 4 格 × 3 单位 = 12 单位 / 7 天 × 均值 1.375 × 2 ≈ 33 金币 / 7 天 ≈ 4.7 金币/天
```

**抑制方案与推荐**：

| 方案 | 效果 | 代价 |
|---|---|---|
| **① 收购侧只收"本村自产"的货 + 每格数量少**（本文已采用） | 从源头限制印钞规模；池子规则已如此 | 无（就是 §5.3 的池子定义） |
| ② 卖出抽 10% 交易税 | 再砍 10% 收益，且多一个货币回收点 | UI 要显示税前/税后 |
| ③ 压低收购价到基准以下 | 彻底没有印钞 | **违背用户"买卖都高于正常价格"的要求** ✗ |

**推荐 ①**（本文默认），并把它写进断言：
- 池子只含"产出它的建筑已解锁"的商品
- 每格数量按 §5.5 的上限
- 增加一条**不变量断言**：`p_buy(s) < p_sell(s')` 对任意 `s, s' ∈ [0,1]` 成立

> 如果实装后发现金币还是涨太快（§十一 第 6 步有实测项），再叠加方案 ②。

## 六、研究所改成默认建筑（科技树调整）

### 6.1 现状（已核实）

- `content/technologies.json` 第 0 项就是 `research_institute`（era 1，`research: 12`，
  `cost.goods = {wood: 10}`，`requires: []`），它的 `unlocks.buildings` 是
  `["research_institute"]` —— **一项科技解锁它自己**，这是当初为了打破"没研究所就不能研究"
  的自锁而设计的"土办法"
- `content/economy.json` 的 `research.baseRate = 2.0`：**没有任何研究所也能研究**
  （同样是打破自锁的补丁）
- 建筑 `research_institute` 的面板：`workers 6 / maxWorkers 6`，
  `capacity = {kind:"research", perWorker:3.0, levelBonus:0.3, slotsPerLevel:3}`

### 6.2 用户要的改动

> 研究所建筑，研究所是默认解锁的建筑，所以不需要研究就可以建立研究所。去掉研究所这个科技。

所以：

1. 建筑 `research_institute` **去掉科技锁**（`technologies.json` 里那条 `unlocks` 一并删掉）
2. **删掉 `research_institute` 这项科技** → 29 项变 **28 项**
3. `economy.research.baseRate` **2.0 → 0**

**为什么 `baseRate` 必须归零**：用户说"建了之后研究才解锁"。
如果 `baseRate` 还留 2.0，那么不建研究所照样能研究（只是慢）——
"建了才解锁"就是一句空话。归零后语义变成：

> **研究所 = 科研的唯一来源。没有研究所 = 完全不能研究。**

**会不会产生死锁？不会。** 论证：

```
开局：baseRate = 0 → 不能研究任何科技
     但 研究所**无科技锁** → 可以直接建（12 木材 / 24 建造力）
     v0.3 开局 12 人全失业 → 建造力 12/天 → 24 建造力 = 2 天
     开局木材 80（§3.5 建议值）→ 12 木材够
建成研究所：1 级 / 6 工位 × 3.0 × 熟练度曲线(50 → 0.8) = 14.4 科研力/天
     → 第一项研究科技可以开始了 ✓ 不死锁
```

> ⚠️ **这条依赖"开局木材 ≥ 12"**。§3.5 把开局木材从 300 砍到 80 之后仍然满足，
> 但**不能砍到 12 以下**。建议在内容校验里加一条断言：v0.3 开局木材 ≥ 研究所的建造木材。

### 6.3 纪元 1 的节奏怎么补

删掉 12 科研力的研究所之后：

| | 原设计 | 新设计 |
|---|---|---|
| era 1 项数 | 6 项 | **5 项**（石作/掘土/薪柴/田猎/石制工具） |
| era 1 科研力 | 122 | **110** |
| 开局到第一项科技 | 2.0/天 × 6 天 = 12 科研力攒研究所 | **建研究所（2 天建造力 + 12 木材）→ 之后 14.4/天** |
| 清完 era 1 | 约 6 + 6.7 ≈ 13 天 | 约 2 + 110/14.4 ≈ **9.6 天** |

**节奏其实更快了**，但换来一次实打实的建筑开销（24 建造力 + 12 木材 + 后续吃 6 个工人）。
这比原来"先攒 6 天再建"更有决策感：**开局就得决定"先建研究所还是先铺粮食链"**。

### 6.4 ⚠️ 一个必须一起改的连带项：建造力死锁

`docs/construction.md` §十一 记录过一条硬约束：

> **建造力归零 = 永久死锁，建筑工坊必须是第一座。**

现在研究所变成"开局必建"，而**建筑工坊是被「营造」科技锁着的**（era 2）。
所以开局的建造力**只能来自失业人口**：

- v0.3 开局 12 人、全失业 → 12/天
- 建研究所需要 24 建造力 = 2 天 ✓ 可行
- **但如果玩家/ AI 第一天就把 12 个人全派到商店上岗**（`jobCapacity` 不再挡迁入，
  但用工分配仍按商店）→ 失业 0 → 建造力 0 → **永久死锁**（连研究所都建不出来，
  于是也永远研究不出「营造」，于是永远没有建筑工坊）

**对策（二选一，建议 A）**：

- **A. 给研究所也开一条"不靠建造力"的路**：不推荐，破坏一致性
- **B. 把"开局必须先建研究所"写进内容校验/开局提示**：在 v0.3 开局给一条 `alert`
  （"先建研究所：没有它无法研究"），并在 `docs/construction.md` 的硬约束清单里
  补一条"研究所是开局唯一的科技入口"

**推荐 B**，另外在 §十一 的实测项里加一条"12 人全上岗后建造力是否为 0"的回归检查。

§7.2 已按用户口述实装，与写稿时的方案有两处**有意的偏差**：

实现要点（都在 `inspector.gd`）：

- `_building_panel()` 按 `defId` 特判 `town_center` / `warehouse`；其余走原通用面板。
- 上限输入框只收数字、**留空 = 不限**，改一次就把整表作为一条 `set_storage_caps` 入队。
- 显示值优先取 `pending` 里的那条命令（次日 06:00 生效）——否则玩家填完下一个小时
  面板重建就被打回旧值，看起来像"改了没生效"（和用工拖动条、人口上限同一个坑）。
- `_rebuild()` 在**有输入框正在被编辑**时让路（`_cap_input_focused()`），

  否则玩家会奇怪"我建了仓库，容量怎么没涨"。

**仍然敞着的一格**：税收 / 租金 / 税率档（§7.2 表格里那条）在城镇中心面板里**还没有入口** ——
本次只搬了人口与公告。要做的话加在城镇中心面板下半部分最自然（那儿现在是公告）。

### 7.7 公告必须随存档保存（2026-10，用户报的 bug）

用户："**公告，退出再进入就全部清空了，这个没有进入存档吗？**"

确实没有 —— 而且是两个 bug 叠在一起，只修一个都还会"缺半截"：

| # | 症状 | 根因 |
|---|---|---|
| 1 | 公告页退出/读档后**一条不剩** | 页面读的是 `SimRunner.recent_logs` —— 表现层自己攒的一份**内存环形缓冲**（60 条），`world_view.load_from()` 里还会显式清空。真正随存档走的是仿真状态里的 `sim.s["log"]`（`state.log`） |
| 2 | 就算改读 `state.log`，也只剩夜里那批 | `state.log` 以前**只**在 `runNight()` 里累积 —— 黎明那批（`activateCompleted` 的「建成投产」/「X 改建为 Y」、`activateResearch` 的「研究完成」）从来没进过存档。玩家眼里最要紧的消息正好全在这批里 |

修法（口径写进 `docs/spec.md` §0）：

- **累积挪到 `stepHour()`**：这一小时跑完，把当小时的**全部**日志（黎明 / 白天 / 夜晚三批）
  并进 `state.log`，上限 500 条。TS 与 GDScript 两边都改，`runDawn()` / `runNight()`
  本身不再写 state（直接调它们只拿到返回值，这是有意的：累积只有 `stepHour()` 一个入口）。
- **公告页直接读仿真**：`SimCore.log_tail(24)` / `log_size()`，`SimRunner.recent_logs`
  这份影子副本**删掉**（`screenshot.gd` 里那段"手工往 recent_logs 抄日志"也随之消失）。
  页面上多一行「共 N 条，显示最近 24 条（日志随存档保存）」。
- `SaveManager._sanitize()` 兜一句 `log` 必须是数组（老存档没有该键时公告页不至于炸）。

门槛 `logsave_test.gd` 走玩家真实路径（点城镇中心 → 公告页 → 存 → 跑脏 → 读 → 再看那一页），
锁三件事：公告 == 当小时返回的全部日志（且含黎明那条「建成投产」）、页面显示的就是
`log_tail(24)`、读档后逐条原样回来。`godot/tests/test_save_load.gd` 另加了 `state.log`
的 JSON 逐字往返断言。

## 十三、门洞与"门前自动铺一格路"（2026-10 更新，已实装）

> 背景：建筑贴图换过一批之后，门画在哪一格和引擎认定的"门格"对不上了；
> 用户要求"重新确定一下门洞的位置"，并且"建造或者移动建筑的时候自动在门洞处
> 自动建造一格道路"、"移走的时候可以先不擦除"。

### 13.1 改动前的口径（缺省仍是它）

门格是**算**出来的，不来自内容：

```
门格   = (占地左上角.x + fw / 2, 占地左上角.y + fh - 1)     # 底边、横向居中（整数除法）
门前格 = 门格 + (0, 1)                                      # 门格正下方那一格
屋内落脚格 = (fw >= 3 且 fh >= 3) ? 占地中心 : 门格
```

宽 4 的建筑 → 第 2 列（0 起），即**偏左**的那一格 —— 不是"正中间"。
两格（门格 + 门前格）都写进 `map.reserved`（`game_map.gd` 的声明注释），
于是"看着是空地，却永远建不了"。

> **为什么门格必须在占地的底边**：`_walk_inside` 只把门格与屋内格标成可通行，
> 其它占格都不可通行。门格若挪到占地内部（比如贴图上真正画着门板的那一行），
> 它下面那一格仍是建筑占格 → A* 从外面走不到门口，居民进不了屋。

### 13.2 现在：内容可以声明门洞（`art.doors`）

```jsonc
// content/buildings.json —— 城镇中心：贴图上是**双开门**，门口占两格
"art": { "arch": "sprite", "foot": [8, 6], "doors": [[3, 5], [4, 5]] }
```

| 项 | 语义 |
|---|---|
| 偏移基准 | **占地左上角**（不是贴图左上角；贴图比占地高时两者差一截） |
| 顺序 | **第一项是主门**：居民从它进出，屋内落脚格由它推出来（小建筑直接就落在主门上） |
| 预留 | 每个门格 + 每个门格的**正下方**那一格进 `map.reserved`；门格同时进 `_walk_inside` |
| 缺省 | 不写 = 13.1 那条老公式（老内容、老存档行为不变） |
| 校验 | 偏移必须是整数、必须落在 `0..fw-1 / 0..fh-1`、不能重复；格式错 → 报错（TS 侧 `check:content` 抛错，GDScript 侧 `push_error` 后**退回缺省**，不让建筑没门） |
| `arch:"sprite"` 的限制 | 声明 `doors` **必须同时写 `art.foot`** —— 否则占地要靠读 PNG 才知道，校验器没法判越界 |

实现：`world_view._door_cells()`（读声明）/ `_default_door_offset()`（缺省公式）/
`ContentDB.validate_doors()`（GDScript 侧校验）/ `validate.ts::parseArt()`（TS 侧校验）。

### 13.3 城镇中心：两格门洞

用户明确要求"城镇中心很明显门口两格都必须是门洞"。它是 121×160 的三层楼整图、
占地 8×6（`foot`），贴图底边对齐占地底边、横向居中：

```
贴图像素 (px, py) → 占地像素 (px + 3.5, py - 64)      # 121 宽居中留 3.5px，160 高比占地高 64px
占用第 4 行（y=128..144，贴图坐标）的两片门板 → 占地的第 3、4 列
→ doors = [[3, 5], [4, 5]]（世界坐标 = 252+3/252+4 列、253+5=258 行；252/253 = 占地左上角）
```

四格被永久预留：门格 `(255,258)`、`(256,258)` + 门前通行格 `(255,259)`、`(256,259)`。

> 顺带一个观察：这栋楼（以及剧院）**贴图上画着门板的那一行在占地底边的上一行**
> （底边那一行是台阶）。门格仍然放底边 —— 那是"门槛/台阶"那一格，语义上正是
> 居民迈进去的落脚点，而且只有它能让 A* 从外面走到门口（见 §13.1 的说明）。

### 13.4 门前自动铺一格路

| 时机 | 位置 |
|---|---|
| 玩家**放下**建筑（`_try_place()` → `_register_site()` 之后） | 每扇门的前一格 |
| **移动到位**（`move_shop_to()` / `move_housing_to()` → `_occupy_building()` 之后） | 同上 |

- **工地阶段就铺**（不用等建成）——玩家一放下就看得见"门在这一侧"，
  这正是用户要的那条视觉提示（"防止用户不知道门洞"）。
- **移走时不擦**（用户："可以先不擦除"）。旧址的其它还原（`_restore_deco()`）保持原样；
  于是旧门前会留下**一小截路**，那是有意的痕迹，不是残留 bug。
- **只动 `map.road`，绝不碰 `map.floor_tiles`**：地板是玩家花钱铺的，两者是分开的
  两套位图（`road_layer` z=-6 画在 `floor_layer` z=-7 上面），互不覆盖。
- 门前格在水面 / 越界时跳过（不在水里修路）；顺手抹掉那一格的树
  （与 `_paint_cell()` 的 road 分支一致）。

实现：`world_view._pave_door_front()` / `_door_front_cells()`，调用点见上表。

### 13.5 门槛

### 13.8 以后要改某一座的门洞，改哪儿、怎么改

**只改一个文件**，看它是不是住房：

| 建筑 | 改这个文件 |
|---|---|
| 普通建筑（面包房、研究所…） | `content/buildings.json` |
| 住房（茅屋 / 木屋 / 砖房） | `content/housing.json` |

**⚠️ 不要动 `godot/content/*.json`** —— 那是 `sync:content` 生成的副本，
改了会被下次同步覆盖，而且门槛读的是根目录那份。

#### 怎么写

在该建筑的 `art` 里加（或改）`doors`：

```jsonc
"art": {
  "arch": "sprite",
  "foot": [4, 3],          // 有 doors 就必须能算出占地：arch=sprite 要写 foot
  "doors": [[1, 2]]        // [[dx, dy], ...]，相对**占地左上角**；第一项是主门
}
```

- `dx` = **从左数第几格 − 1**（0 起）；`dy` = **从上往下第几格 − 1**。
- **`dy` 永远填 `占地高 − 1`**（最后一行）。门格必须在占地底边，否则居民从外面
  A\* 走不到门口（见 §13.1）。
- 所以实际操作上你只要告诉我**门在从左数第几格**就行，`dy` 是算出来的。
- 门画了两格就写两项，前面那项当主门：`"doors": [[3,5],[4,5]]`。
- 已经声明过的：`town_center` `[[3,5],[4,5]]`、`research_institute` `[[3,2]]`、
  `hut` `[[1,2]]`（+ 显式 `foot [4,3]`）。

#### 怎么知道门在第几格

1. 游戏里按 **ESC →「建筑占地」** 打开调试开关：每座建筑会画出彩色占地格，
   数一下门对上的是从左第几格；
2. 或者直接说"哪座建筑 + 门在从左第几格"，配一张开了开关的截图最省事；
3. 手工看图的话：贴图**每 16px = 1 格**，贴图**底边对齐占地底边**、横向居中
   （`_place_sprite()`），从占地左边缘数过去就是 `dx`。

#### 改完必须同步 + 过门槛

```sh
# 1) 同步到 Godot 工程（必须，否则游戏里看不到改动）
node --experimental-strip-types scripts/sync-content.ts

# 2) 内容校验 + 全部门槛
node --experimental-strip-types scripts/check-content.ts
bash godot/verify.sh          # 最后一行要是 ALL CHECKS PASSED

# 3) 想眼看一遍：截图模式（见 §13.7）
```

⚠️ 这台机器**不要跑裸 `pnpm test`**：它会把 `node_modules` 里的 typescript
从 5.9.3 换成 5.7.2（`tsconfig` 的 `erasableSyntaxOnly` 需要 ≥5.8 → TS5023），
还会生成 `pnpm-lock.yaml`。用上面的 `node --experimental-strip-types` 直接跑。

⚠️ `godot/tools/door_test.gd` 里有两条硬断言：**城镇中心必须正好两格门洞**、
**每座建筑的门洞都得落在自己占地内**。把城镇中心改成 1 格会让门槛变红 ——
那是故意的，改需求就要连门槛一起改。

## 十三·九、改建筑占地（`art.foot`）：改哪儿、怎么秒验（2026-10 实装）

### 13.9.1 占地是怎么定出来的（唯一入口）

`godot/scripts/world/world_view.gd::_footprint()`，`TILE = 16`（**别用 32 去算**）：

| `arch` | 占地 |
|---|---|
| `sprite` | ① 有 `art.foot` → 就用它；② 没有 → `floor(贴图宽/16) × floor(贴图高/16)`，每维至少 1 |
| `field` 或写了 `rows` | `w × rows`（`w` 缺省 6） |
| 其余程序化 | `w × (屋顶行数 + 1)`，`roof:"green"` 1 行、其余 2 行；`w` 缺省 3 |

TS 侧有一份**同口径**的镜像 `src/engine/content/validate.ts::artFootprint()`（只用于校验门洞越界），
改口径要两处一起改。

### 13.9.2 现在每一座都写在文件里了

2026-10 起，**全部 32 座 `arch:"sprite"` 建筑/住房都在 `art` 里显式写了 `foot`**
（29 座在 `content/buildings.json`，3 座在 `content/housing.json`），值就是上面那条推导公式
算出来的值 —— 纯 no-op，游戏里没有任何变化。**要调某座建筑的占地，就改那一行。**

```jsonc
"art": {
  "arch": "sprite",
  "foot": [6, 3]      // [宽, 高]（格）：宽 2–12、高 1–12
}
```

⚠️ **代价（务必知道）**：写了 `foot` 之后占地就**不再跟随贴图**。以前换一张新图、
占地会自动按新尺寸变；现在得回来核对那一行。`npm run check:footprint` 会专门把
"声明值与贴图推导值不一致"的座列出来，换完图跑一下就知道要不要改。

改哪个文件：普通建筑 → `content/buildings.json`；住房（茅屋/木屋/砖房）→ `content/housing.json`。
**别动 `godot/content/*.json`**（`sync:content` 的副本，改了会被覆盖）。

### 13.9.3 改的时候会踩的硬约束

1. `foot[0]` 是 **2–12** 的整数、`foot[1]` 是 **1–12** 的整数（`validate.ts` 直接报错）。
2. **`arch:"sprite"` 不许写 `w` / `rows`** —— 那两个是程序化拼装的字段，占地要单独声明就用 `foot`。
3. **占地不能比贴图高**：`_place_sprite()` 把贴图**底边**对齐占地**底边**，多出来的行全在顶部、
   画面上什么都没有却挡建造（玩家报过"明明没占到，实际占到了"）。这是门槛 `footprint` 判红的那条。
   占地**比贴图矮**是允许的 —— 那正是"往上伸出去遮挡身后建筑"的正经用法。
4. **门洞会连带失效**：`art.doors` 的偏移基准是**占地左上角**，且**门格必须在占地底边**
   （`dy = foot[1] − 1`）。改小 `foot` 会把原来的门挤出界 → `check-content` 与 `doortest` 变红，
   要同步改 `doors`（写法见 §13.8）。
5. **城镇中心有第二处硬编码**：`godot/scripts/world/game_map.gd` 的
   `town_center = Rect2i(W/2-4, H/2-3, 8, 6)` 必须与 `town_center.art.foot` 一致。
6. 屋内落脚格 = `fw ≥ 3 且 fh ≥ 3` 时取占地中心，否则取门格本身（§13.1）—— 占地掉到 2 行会改进出路径。
7. **占地写进存档的占用格**：v3 起锚点改成了"脚"（§13.11），**v2 及更早的档直接读不了**（重存一次即可）。

### 13.9.4 秒验（这就是"改完随时验证"的那条命令）

```sh
# ① 改完 content 先同步（必须，否则游戏里看不到）
npm run sync:content

# ② 秒级校验：不起引擎、<1 秒；打印每座建筑的贴图尺寸/推导占地/声明占地/判定
npm run check:footprint

# ③ 想眼见为实再跑全门槛
npm run check:content      # 占地范围、门洞越界
bash godot/verify.sh       # 最后一行要是 ALL CHECKS PASSED
```

`check:footprint`（`scripts/check-footprint.ts`）的三类输出：

- **红（退出码 1）**：贴图缺失 / `foot` 越界 / **顶部隐形行** / `godot/content` 副本没同步；
- **`*` 显式覆盖**：这几次的占地是手写的、与贴图推导值不同 —— **换过这几张贴图就要回来核对**。
  当前只剩 1 座：`town_center`（声明 8×6，按缺省规则推是 7×9）。`domestic_service`（8×3）与
  `research_institute`（8×3）在 §13.10 把"顶行不占地"写进缺省规则之后，**已经与推导值一致**了；
- **无标记**：贴图比占地高/宽（往上伸出、左右留出，全是设计允许的常态，表格里会写清多少 px）。

游戏内肉眼确认：**ESC →「建筑占地」**（`world_view.set_debug_footprints`）会画出彩色占地格、
门格与门前预留格；批量看可用 `godot/tools/screenshot.gd` 的 `doors` 模式（§13.7）。

## 十三·十一、占地锚点在「脚」（底边那一格）—— 2026-10 换的口径

### 13.11.1 为什么换

**旧口径**：`cell` = 占地**左上角**。于是"把 `foot` 高度减 1 行"会把整栋房子**往上抬一行**
（贴图底边对齐占地底边，底边一动画就跟着动），空出来的是**脚下**那行、而不是屋顶那行 ——
跟"屋顶不占地"的直觉正好相反。

**新口径**：`cell` = **底边那一行的最左格**（"脚踩的那格"）。于是：

- 占格 = 从锚点**往上**数 `foot[1]` 行；锚点**下面**那一行不占；
- **改 `foot` 高度只影响顶部**（屋顶往上伸出去），房子原地不动；
- 玩家点的那一行就是它的脚（左边缘再往左一格）。

### 13.11.2 换算只允许走三个函数

`godot/scripts/world/world_view.gd`：

| 函数 | 作用 |
|---|---|
| `_foot_top(cell, fp)` | 脚 → 占地左上角（`map.occupy()` / `terrain_ok()` / 门洞偏移要用左上角） |
| `_foot_anchor(top, fp)` | 左上角 → 脚（"先按左上角搜、再回报锚点"的地方用） |
| `_foot_rect(cell, fp)` | 脚 → 占地矩形（命中区、调试画框用） |

⚠️ **别在别处自己写 `cell.y - fp.y + 1`** —— 现在所有占格/门洞/移动/拆除/调试都走这三个换算，
漏一处就是"占地和画面错开"。

### 13.11.3 "顶行不占地"现在是缺省规则

没写 `art.foot` 时，`sprite` 建筑的占地 = `floor(贴图宽 / 16) × (floor(贴图高 / 16) − 1)`
—— 最高那一行（屋顶 / 塔尖）**不占地**，跟"小人只有下半身占地、脑袋不占地"同一个道理。

现在 32 座 sprite 建筑全都显式写了 `art.foot`，值就等于这条缺省规则；唯一手写覆盖的是
**城镇中心**（8×6，按规则推是 7×9 —— 它是 160px 高的三层楼，按规则要占 9 行地，太浪费）。

### 13.11.4 命中区：点屋顶 / 塔尖也要选中这座建筑

点击与悬停认的是 **占格 ∪ 贴图覆盖格**（`_pick_building_at()` + `_sprite_rect()`）：

- 屋顶、塔尖画在占格**外面**，但**点它照样选中这座建筑**（用户："点屋顶选不中房子，这个无法接受"）；
- 同一格被多座压住时，取**底边更靠下**的那座 —— 和遮挡顺序一致（画在上面的那座先被点到）；
- 命中区**不写进 `map.occupied`**，所以那些格子照样能盖别的建筑、盖上去会被屋顶挡住 ——
  这正是"村里密密麻麻、熙熙攘攘"的层叠效果（用户明确想要的）。

调试开关里：**填色**的是占格、**蓝框**是命中区、**橙框**是门洞与门前预留格。

### 13.11.5 连带影响

- **存档版本 2 → 3**：旧档存的是"左上角"语义，读进来会整村错位 → `load_from()` **直接拒绝
  v2 及更早**（重存一次即可，不猜）。
- **开局那 6 间茅屋**的位置由 `_find_free_area()` 现算（返回值已经是"脚"），不用手改。
- **进度条的基线**也吃这个口径：`_bar_base_y()` 必须先用 `_foot_top()` 换成占地左上角、
  再往上 16px —— 直接写 `cell.y * TILE - 16` 会把条画进**建筑顶上那一行**里。
  顺手把工地 / 建筑升级 / 研究所三条条合并成 `_draw_bar_at()`，并补上了**建筑升级的
  进度条**（升级是从建筑面板下单的，以前地图上一点进度反馈都没有）。
- 门槛：`godot/tools/roofclick_test.gd`（占格 / 地面线 / 点屋顶选中 / 点塔尖选中城镇中心）
  ＋ `multisite_test`（同类多工地各对应各自的队列条目）+ `upgrade_test`（升级进度条）
  ＋ `door_test`（门格与门前格）+ `footprint_test`（顶部隐形行）。

## 十四、住房改建（茅屋 → 木屋 → 砖房）

> 用户："茅屋可以升级成木屋，木屋升级成砖房，但是别墅要单独建造。"

### 14.1 链写在内容里，不按 `quality` 自动推

`content/housing.json` 的 `upgradeTo` 显式给出下一档：茅屋 → 木屋 → 砖房（砖房不指向谁）。
**别墅以后加进来时，只要没人指向它，它天然就是"只能单独建造"** —— 换成"按 quality 推下一档"
的话，别墅（第 4 档）会自动变成砖房的改建目标，正好是用户不要的。

数值口径（唯一契约是 `docs/spec.md` §5.4）：

| 项 | 规则 |
|---|---|
| 材料 | 目标 `buildCost` −**原房型** `buildCost`（只算差价，旧料视为回收）。木屋 6木6砖 − 茅屋 4木3砖 = **木 2 + 砖 3**；木屋→砖房只补**石头 3** |
| 工期 | `max(1, 目标 buildWork − 原房型 buildWork)`：24−12 = 12、36−24 = 12 |
| 土地 | **不额外占名额**（原地改建，栋数不变） |
| 私有 | **不能改建**（居民买下的私产） |
| 在途 | 也算占用：2 栋茅屋只能排 2 条改建，否则完工时会凭空多一栋 |
| 容量 | 会变小（茅屋 4 人 → 木屋 3 人），住满时多出来的人**没房住**（满意度按 `housingQuality` 扣） |

### 14.2 玩家怎么用

点地图上的住房 → 右侧 Inspector（`inspector.gd::_housing_panel()`）：

- 不是链尾 → 多一栏「改建 → 木屋（木材 2，砖 3 · 建造力 12）」＋按钮「改建为木屋」；
- 私有住房 → 按钮**置灰** +「私有住房不能改建（居民买下的私产）」；
- 已经在改建（或已下单）→ 按钮**置灰** + 说明。

命令次日 06:00 生效，和其它命令同一条路（`runner.enqueue`）。

### 14.3 地图上的反馈

住房是**计数模型**（`state.housing[gid]` 是数量，没有实体），所以改建没有工地实体 ——
进度条直接画在**第 i 座同类国有住房**头上：

- 配对约定：`world_view._housing_ordinal()` = 这座房子在**同类型国有实例**里的序号，
  对应同类型第 i 条在途改建。两侧都是 FIFO，条目被收走时序号自动重排；
- 颜色与工地 / 建筑升级 / 研究所**同一套**（`_draw_bar_at()`）：灰 = 已下单未生效、
  黄 = 排队 / 缺料、蓝 = 在建（带填充比例）；
- 悬停那座住房：「茅屋 → 木屋 改建 · 建造中 / 建造力 4 / 12（34%）」。

### 14.4 门槛

- `scripts/check-housing-upgrade.ts`：引擎（TS）的差价、工期、数量转移、土地名额不变、
  三条拒绝路径（私有 / 链尾 / 在途占满）。`npm run check:housing-upgrade`。
- `godot/tools/housingupgrade_test.gd`：GDScript 镜像 + 世界层进度条 / 悬停 + 住房面板按钮
  （含私有时置灰）。已加进 `verify.sh`。

## 十五、建造队列（城镇中心第 3 个页签）

> 用户："现在建造的时候逻辑上其实有一个队列，建筑会按照队列来建造，**无法调整建造顺序**。
> 需要有一个面板来调整。我的想法是城镇中心加一个 tab……每一项左侧是缩略图，已经使用的
> 建造力，需要的建造力，然后右侧三个按钮：向上箭头（提高一个次序）、向下箭头（降低一个
> 次序）、叉（取消建造）。"

队列本来就是 `sim.s["construction"]` 里的**一条先进先出数组**：队首先开工、产能没用完
才溢给下一条。所以"顺序"就是唯一能操作的东西，这一页把它交给玩家。
公式契约在 `docs/spec.md` §9.8，设计理由在 `docs/construction.md` §十二。

### 15.1 面板长什么样

```
建造队列
从上往下依次施工：队首先吃到建造力 8.8/天。命令次日 06:00 生效。
[缩略图] 1. 粗面粉磨坊  完工（次日黎明启用）      [▲][▼][取消]
         已用 12 / 需要 12 建造力（100%）
[缩略图] 2. 粗面包房    建造中                    [▲][▼][取消]
         已用 1.1 / 需要 12 建造力（9%）
[缩略图] 3. 组织坊      排队中（前面还有 2 处工程） [▲][▼][取消]
         已用 0 / 需要 24 建造力（0%）
```

- **左**：`UIKit.thumb()` 的缩略图（改建显示**改完**的房型 —— 那是它建成后的样子）。
  尺寸的规矩是"**尽量取源图的整数倍**"，两条队列的源不一样，所以不能给同一个数：
  - 建筑 / 住房缩略图是 `assets/thumbs/*.png`：**固定 100×72 的画布**，里面是按整数倍
    缩小居中的原图（`scripts/gen-art.ts::thumbOf()`，几何倍率 1/2/4…）。现在取 **48**
    （= 0.67× 画布，**非**整数倍；最近邻下细节会丢一点点，换来行矮、一屏条数多）。
    要像素级干净就取 72 的整数倍：**72（1×，行高 80，一屏 7 条）** 或 144（2×，行高 152，
    一屏只剩三四条 —— 试过，用户说"改回去"）。`project.godot` 的
    `textures/canvas_textures/default_texture_filter=0` 是**最近邻**。
  - 科技图标原生 **32**（`UIKit.TECH_ICON_SIZE` 的注释："只做 1 倍，整数倍才不糊"）→ **2× = 64**。
  - ⚠️ 框**不能给正方形**：画布是 100×72（横的），塞进方框里等比缩放会被**宽度**卡住 ——
    行变高了、图还是原样大（第一版就是这么"放大"了个寂寞的）。
- **中**：`序号. 名字` + 状态；下面一行是**已用 / 需要建造力（百分比）**
  （已用 = `totalRequired − remaining`，与工地悬停提示同一口径）；文字整块**垂直居中**
  （缩略图比文字高，不居中的话行看着像空的）
- **右**：`▲` 提前一位 / `▼` 推后一位 / `取消` 撤单；队首的 `▲`、队尾的 `▼` 置灰
  （用户："上箭头改成上三角形，下箭头改成下三角形，叉改成取消两个汉字"。
  `▲` `▼` 是 U+25B2 / U+25BC —— 字体里真有；而 `✗` `−` 那类缺字形画出来是**空的**，见门槛 `glyph`）
- 行高 = 缩略图 + 8（建筑 56、科技 72）；三个按钮固定 34 高、**垂直居中**
  （行变高之后不再被拉到整行高）
- 「名字 + 状态」那一格很窄（缩略图 + 三个按钮占掉一半宽度），**长的提示会被 `clip_text`
  切掉** —— 所以二次确认那句「再点一次「取消」：退回 …」**单独占一整行**（横跨整行，
  `VBoxContainer` 包住原来的 HBox），不跟状态挤一格。（缩略图放大到 144 时这个问题特别明显：
  "石块×2.72" 那截直接没了。）
- 状态文案**复用 `world_view._why_waiting_at()`**（工地悬停读的是同一支）：
  `完工（次日黎明启用）` / `建造中` / `排队中（前面还有 N 处工程）` /
  `等待材料（缺 木材 6）`。`remaining <= 0` 与 `started` 必须分开判 ——
  完工的条目要等到次日黎明才移出队列，白天它和"下一条在建"同时在队列里，
  都写「建造中」会让人以为两处工地一起动（实测截图里就是这样）。
- 这一页的**高度跟着内容走**（`panel_civic.gd::_tab_height()`）：条数不定，
  写死高度的话空队列留一大片空白、排 12 条又只剩几行要滚。上限 620（再长就滚动看）。
- ⚠️ 行高的代价：一屏能看到的条数少了（620 的面板 × 152 的行 = 3~4 条，其余滚动）。
  嫌少就把 `THUMB_BUILD` 调回 72（画布 1×）—— 行高 80，一屏 7 条。

### 15.2 撤单是两步，且只退"没干完的那份"

点第一下 `取消`：那一行变成红色的「再点一次「取消」：退回 木材×5.44、石块×2.72」，
第二下才真的撤（`runner.enqueue`，次日 06:00 生效）。预览走
`sim.construction_refund_preview()`（**只算不改**，与真退是同一份口径）。

| 情况 | 退什么 |
|---|---|
| 还没开工 | **退 0** —— 材料是开工那一刻才扣的，没开过工就一分没扣 |
| 已开工 | 已扣材料 × `remaining / totalRequired`（只退没干完的那份） |
| 已完工（`remaining <= 0`） | `取消` **置灰**：退 0，不想要它应该等建成后走「拆除」 |

撤单会往**公告**写一条：`取消「瓷窑」（已投入 28%），退回 木材×4.33、石块×2.17`。

### 15.3 面板画的是"显示副本"

命令次日 06:00 才生效。不把 `pending` 里的调序 / 取消先算进去，点完 `▲` 屏幕上一动不动，
玩家会以为没点上 —— 所以 `_queue_view()` 复制一份队列、把待生效的命令先应用上，
**只用来画界面**（真状态仍由 sim 在黎明改）。已排队的调序会在状态里加「（调序已排队）」，
取消则在页尾写「N 项已排队取消，次日 06:00 生效（材料那时才退）」。

刚下但还没进队列的单子（`pending` 里的 `build` / `build_housing` / `upgrade_housing` /
`expand`）也不该让页面看着是空的 —— 页尾写「另有 N 项刚下的单，次日 06:00 才进队列」。

### 15.4 取消之后地图上要收工地

`world_view._sync()` 末尾会 `_prune_orphan_sites()`：同类型的工地里**多出来的那几处**
（`_site_by_type[type].size() > _construction_entries(type).size()`）就是孤儿，
从队尾收回 —— 精灵 `queue_free()` + `map.free_cells()` 放回地格。
不收的话，取消掉的工地会**永远留在图上**（灰色精灵）且地格永远占着，像"还在建、只是不动了"。

## 十六、产能建筑的第二个页签（建筑工坊 / 研究所）

> 用户："**2、点击建筑工坊的面板也加这一个 tab**。3、研究队列……在**研究所**的面板加一个 tab，
> 里面是研究队列。"

这两条是同一件事：**同一个队列控件**挂到两种建筑的建筑面板上。

| 建筑 | 第二页页签 | 看的是 |
|---|---|---|
| 建筑工坊（`capacity.kind == "build"`） | 建造队列 | `sim.s["construction"]` |
| 研究所（`capacity.kind == "research"`） | 研究队列 | `sim.s["research"]["queue"]` |
| 其它建筑 | **没有页签行** | — |

- 页签行放在**滚动区外面**（`inspector.gd::_ready()` 里紧跟分隔线）——滚内容时页签不该跟着滚走，
  与城镇中心对话框同一形式；只有一页时整行 `visible = false`，不给普通建筑留一条空条。
- 行的画法、调序、两步撤单**只有一份实现**：`scripts/ui/queue_box.gd`（`class_name QueueBox`）。
  城镇中心的「建造队列」页、建筑工坊、研究所三处都用它，换 Kind 决定读哪条队列、显示
  「建造力」还是「科研力」、缩略图走建筑图还是科技图标。研究队列多一行**研究内容/效果**
  （`效果 建材 +20%`、`解锁 采石场`）。
- 二次确认状态记在**面板**的 `_qstate = {"confirm": ""}` 里再传给控件：控件每个游戏小时
  都会被重建，状态记在控件上会被下一次重建抹掉。

### 16.1 顺手修掉的一个布局坑

`inspector.gd::_clear()` 原来只有 `queue_free()`。`queue_free()` 是**延迟**的，节点要到帧末
才离开树，而面板高度是按 `_body` 的内容算的（`_fit_height()`）—— 同一帧里去量，量到的是
**旧内容 + 新内容**：切到队列页时「运营」那页还在树上，于是面板一路顶到 832px 上限、
底下空 200px（实测）。现在改成 **先 `remove_child()` 再 `queue_free()`**，切页后面板立刻贴合内容
（切页后面板立刻贴合内容）。

城镇中心那边（`panel_civic.gd::_refresh()`）是同一个坑：「建造队列」页的高度改成跟着内容走
之后，它也得先 `remove_child()` —— 否则量到的是"上一页 + 这一页"两份内容。

- ⚠️ **为什么不是 TextureRect**：这几个面板都是 `PanelContainer`，它把直接子节点**强行拉伸**
  到底；被拉满的 TextureRect 只有 `STRETCH_KEEP_ASPECT_CENTERED` 可用 —— 那会画在正中间，

- ⚠️ **画在最上层**（`add_child` 在内容之后）。反过来（垫在文字底下）会让数字压在脸上，更难看。
  代价是**内容那一侧要给右下角让位**，各处都是这么处理的：
  - 统计 · 资源：详情列撑开 + 右边留 `PORTRAIT_GAP`（292）的固定空隙（数字停在立绘左边，
    用户 2026-10："净变化/日那列要靠着右侧"）
  - 统计 · 人口：名单 560 固定宽 + 详情 420 固定宽 + 右边让位
  - 任务：`_detail_w()` 里减掉 300（右栏文字不许排到脸上去）
  - 预言：右栏外面套一个固定 316 宽的空气列
  - 科技：**例外** —— 科技树是可平移的画布，立绘压在右下角那张卡上。要看得见就拖走。
- ⚠️ **底边 / 右边要贴着面板的边**（用户 2026-10："下底边要贴着面板下沿，现在有一个
  padding"）：`PanelContainer` 的 `content_margin` 会把子节点往里挤一圈，立绘画在这个被挤小的
  矩形里，自然就离边还有一条 padding。所以 `PanelPortrait` 在 `_ready()` 里从**父节点**的
  `panel` 样式盒读 `content_margin_right/bottom`（不能问自己 —— 那个覆盖挂在 PanelContainer
  身上），`_draw()` 时加回去。面板换了内边距，立绘自动跟着贴边。
- 立绘是照片级美术，**不是像素图**：`PanelPortrait` 把 `texture_filter` 设成 LINEAR，

## 二十三、数字的字体与字号

用户 2026-10："资源面板右侧数字用的是什么字体？非常符合像素画风，把整个游戏的所有数字
都用这个字体（但是大小可以小一点）。"

**答案：就是那一个像素字体**（`fusion-pixel-12px`），资源面板那几个大字只是画在
`BIG_FS = 24`（= 原生 12 的**整数 2 倍**），所以笔画是干净的 2px、一点灰边都没有。
"看起来像另一种字体"是尺寸造成的错觉。

**结论：数字不单独放大，和正文一样 12。** 试过一版"所有数字用 18"（顶栏数值 + 统计面板
每一格），上线前用户看了一眼就否了："算了，数字改回来吧，不好看。"
那条改动整个revert 掉了，`UIKit` 里也**没有** `NUM_FS` / `num_label` 这种东西，
`panel_test` 反过来锁了一条：统计面板里**不许出现非 12 / 非 24 的字号**。

| 用途 | 常量 | 值 | 谁用 |
|---|---|---|---|
| 正文 / 数值 | `UIKit.FS` | 12 | `UIKit.label()` —— 说明文字、表头、表格里的数 |
| 大标题 / 大字 | `UIKit.BIG_FS` | 24 | 面板标题、资源详情的主数字、村名 |

- 真要把某个数放大，只有 24 这一档是安全的（整数 2 倍）；**14 / 16 / 18 / 22 都会拆笔画**
  （字体按 12px 网格设计，非整数倍落不到整像素）—— 这也是当初 18 看着"有点怪"的原因。
- 资源面板那几个 24px 的数（库存 / 日产量 / 净变化）**保持原样**：它们是"大字"，不是正文数字。

## 二十八、住房改建在地图上的表现（原地换房 + 按房号配进度条）

用户 2026-10 报了两个症状，其实是**同一处**（`world_view._sync()` 的住房段）的两面：

1. 「茅屋改建木屋之后，房子并没有消失，而是多了一座木屋」
2. 「有大量茅屋在升级的时候，升级条到处乱跳，你是不是没有给他们 id？」

### 根因：住房当初是**计数模型**，没有单体身份

仿真里原来是 `housing = {hut: 6}`（一栋一个条目都没有），改建就是"一类 −1、另一类 +1"。
于是引擎根本不知道"地图上哪一栋在改建 / 哪一栋是私产 / 哪一栋住着谁"，
地图这边只能按顺序猜（"同类型第 i 座 ↔ 第 i 条在途改建"），
而队列是队头出、房子却一座不少 → 每完工一条就整体错位，条就跳到别的房子上。

**2026-10 已改成单体模型**（`docs/spec.md` §5.5）：每栋房一个 `HousingUnit`
（`{id: "h#7", type, private, ownerId?}`），改建**换 type 不换 id**。
现在地图实例的 `uid` 就是房号，进度条直接用 `construction[].housingUnitId` 对号入座，
**没有任何顺序约定**了。

### `_sync()` 里的三条规矩

| 规矩 | 为什么 |
|---|---|
| **收**：地图上有、`housingUnits` 里没有这栋了 → 连精灵 + 名字标签 + 地格/门洞一起还回去 | 只加不减就是"旧房没消失、旁边多一座"（症状 1） |
| **换**：房号还在、房型变了（改建完工）→ **原地重建**（同 uid、同格子，`_rebuild_housing_instance`） | 改建就该在原地变样，而不是别处长出一座 |
| **加**：`housingUnits` 里有、地图上没有 → 先占刚腾出来的格子，再认领工地，最后找空地 | 新房不该乱挑位置 |

### 进度条 / 悬停

- `_housing_upgrade_entry(inst)`：在 `construction` 里找 `housingUnitId == inst.uid` 的那条
- `_housing_upgrade_pending_unit(inst)`：`pending` 里"刚下单、还没到黎明"的 `upgrade_housing`
  也带房号（住房面板下单时会带 `unitId`），所以**下单那一刻**条就钉在那栋房上
- 旧实现（`_housing_ordinal()` 顺序配对、`_pop_housing_instance()` 的 FIFO 约定）已删除；
  `_pop_housing_instance()` 只留作老世界存档的兜底

### 实例 id 与存档

- 房号由**仿真**发（`state.housingSeq`，`h#N`，单调、收房不回收）；地图实例的 `uid` 直接用它
- 老世界存档没有 `uid` 时，`_place_housing_instance` 自己发一个 `w#N` 占位，
  下一帧 `_sync` 会按 `housingUnits` 纠正（位置会重挑一次 —— 旧档本来就是不兼容的）
- 私有标记**按房号**：`_assign_homes()` 读 `unit.private`（不再"前 N 栋按顺序标"）

### 门槛

`godot verify.sh` 的 `housingupgrade` 第 5 节（3 座茅屋同时改建）：
- 3 条改建条目里各自记着**房号**；第一栋头顶的条是它自己那条
- 完工第一栋后：**同一格、同一房号**、房型变木屋；剩下两栋的条仍是各自那条（不许跳）
- 地图实例总数不变、茅屋实例数 = 引擎里的茅屋数、无残留进度条
- 两个方向都验证过会红：只加不减 →「房子数量变了」；顺序配对错位 →「条在跳房子」

TS 侧 `scripts/check-housing-upgrade.ts` 另有一套引擎断言（id 唯一、改建换 type 不换 id、
指名改建 / 指名私有被拒 / 计数 == 由 units 数出来的）。

## 二十九、地图上的矿脉（石 / 粘土 / **铁**）

用户 2026-10："地图上加入铁矿资源"。

矿脉是**地形**，不是"资源点实体"：`GameMap.terrain` 里一个字节（`GameMap.IRON = 5`），
和石矿（2）、粘土（3）同级。建筑靠 `content/buildings.json` 的 `terrain` 字段绑地形 ——
`quarry.terrain = "stone"`、`clay_pit.terrain = "clay"`、`iron_mine.terrain = "iron"`。

| 地形 | 值 | 贴图 | 谁建在上面 |
|---|---|---|---|
| `stone` 石矿 | 2 | `extra.png` 索引 50 | 采石场 |
| `clay` 粘土 | 3 | `extra.png` 索引 51 | 粘土坑 |
| **`iron` 铁矿** | **5** | `extra.png` 索引 53 | **铁矿场**（`iron_mine`）|

### 生成（`game_map.gd::generate`）

```
野外：4 处（半径 5，随机位置）       ← 比石/粘土（各 6 处、半径 6）稀
出生点：3 处（+16/-12 半径 4、-40/+28、+36/-32）
```

⚠️ **顺序有坑**：铁矿脉必须排在"出生点那几片树林与石/粘土"**之后**。
那几片 `_blob`（尤其半径 16 的树林）会把先放下的矿脉整个盖掉 ——
第一版就是"加了铁，地图上一格都找不到"（门槛 `iron` 的"最近一格离中心 ≤ 30"会抓到）。

### 画出来（`world_view._texture_for` 之外的那条路）

地形是 TileMapLayer 两层：`source 0` = Tiny 图集（草地底），`source 1` = `extra.png`（叠加层）。
矿脉 = 草地底 + 叠加块：`terrain_layer.set_cell(c, 1, _extra_cell(53))`。
`extra.png` 由 `scripts/gen-art.ts::patchTile()` 画（暗蓝灰岩 + 四粒锈斑 ——
没有锈斑的话它和石矿在缩略图上分不出来），跑 `npm run gen:art` 重新生成。
小地图颜色：`minimap_widget.TERRAIN_COLORS[5]`（比石矿更暗更冷）。

### 内容与门槛

- `iron_ore`（铁矿石）：`goods.json`，tier 0 / raw / storable / baseValue 2.8
- `iron_mine`（铁矿场）：`buildings.json`，`sector:"material"`、`terrain:"iron"`、
  `arch:"extract"`（程序化外观：石墙 + 蓝顶 + 烟囱 + `feat:["rocks"]`，占地 4×2）、
  6 铁矿石/日、用工 3（上限 6，与其它采集业同档）
- 解锁：**烧砖**（`brickmaking`）—— "有了砖窑的火才烧得动铁"，也让它在建造栏里
  和采石场 / 粘土坑一样是**锁着的**（不然开局唯一亮着的那座矿场就是它，很怪）
- 建造栏：`CAT_MINING` 白名单加了 `iron_mine`，「矿场」页；tooltip 的
  「需地形：」走 `ContentDB.TERRAIN_ZH`（中文，不再打印 `stone` / `iron` 这种英文 key）
- 门槛 `iron`（`godot/tools/iron_test.gd`）：地形常量与名字、生成数量/位置/可复现、
  贴图索引 53、内容三项（terrain/产出/分类）、放置判定（铁矿脉可建、草地被拒）。
  ⚠️ `place_reason()` 收的是**鼠标格**（内部 `cell - (1,0)` 再推占地），
  拿左上角直接喂会被误判成"资源不符" —— 门槛里两种都验了

### 现在能拿铁干什么

**暂时只到"挖出来、进仓库"为止**：`iron_ore` 还没有下游消费者
（`docs/technology.md` 里规划的"铁制工具 +60%"需要铁矿 + 高炉，还没做）。
所以它现在是一条**只产不耗**的原料线 —— 拉满它只会占仓储，别急着建第二座。
