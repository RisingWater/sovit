# 建造力系统设计

> 状态：**已实现（第一步 + 第二步均已落地）**。
> 本文是实现依据；`docs/spec.md` §9 是 TS ↔ GDScript 对拍用的公式契约。
> TS：`src/engine/systems/investment.ts` / `labor.ts` / `finance.ts`；
> GDScript：`godot/scripts/sim/sim_core.gd`。

## 一、核心概念

```
建造力 = 每日施工产能（速率，不是库存）

  每日产能 = 失业人口 × 1.0
           + Σ(建筑工坊工人 × 2.5 × (0.6 + 0.4 × 熟练度/100))

  一个工程需要「n 建造力」= n 个"人·天"
  工期 = 需求量 ÷ 每日产能（产能逐日投入，不用完就浪费）
  每天的产能摊在**工作小时**里（06:00–18:00，每小时 1/12），不是一天一跳
  当天的量在**黎明钉住**（`constructionRateToday`），白天只用它，不每小时现算
  多个工程 → 一条先进先出队列，串行
```

**建造力不进库存。** 每天重新产生，当天没用完就作废（不结转）。
因此不存在"攒一堆建造力一口气开工"，扩张只受**时间 × 产能**限制。

**为什么按小时摊开**：生产（`runProductionStep`）本来就是"日计划 + 小时执行"，
施工却曾经把一整天的产能堆到 18:00 一次性投入 —— 同一局里两个节奏，玩家必然按
生产那套预期读工地，于是一整个白天都看着 `0 / 12`，到晚上突然跳到 `12 / 12`。
现在施工与生产**同一条件、同一节奏**（`workStart ≤ h < workEnd`，每小时投
**黎明钉住的当日预算** / 工作小时数），一天的**总量不变**，但白天能看见进度在爬：

```
建造力 12/天，一座 buildWork = 24 的建筑：
  day1 06:00 → 0/24 ，18:00 → 12/24
  day2 06:00 → 12/24，18:00 → 24/24（当天收工前完工）
```

**为什么当天的量在黎明钉住**（`constructionRateToday`，见 `docs/spec.md` §9.3）：
每个工作小时投出去的量 = `constructionRateToday / 工作小时数`，而 `constructionRateToday`
是黎明（`assignLabor` 之后）那一刻的 `constructionRate()`，全天不变。
若不钉、每小时现算，当天中途任何人事变动（失业人口增减、建筑工坊在岗人数变化）
都会当场改写"这一天的总量" —— 工地上会一小时快一小时慢。钉住之后，
"当天的总量恰好等于黎明那一刻的建造力"是一条**硬闸**，不依赖任何隐含前提
（科研 `researchRateToday` 是同一道闸，见 `docs/technology.md` §2.5）。

## 二、产能

| 来源 | 每日建造力 |
|---|---|
| 失业人口（上工地） | **1.0**（固定，不随熟练度变 —— 非熟练工） |
| 建筑工坊工人 | **2.5 × (0.6 + 0.4 × 熟练度/100)** |

| 熟练度 | 建筑工坊工人 |
|---|---|
| 30（居民起步） | 1.8 |
| 50（新工坊默认） | **2.0** ← 正好是失业人口的 2 倍 |
| 100（满级） | 2.5 |

- **不封顶**：有多少失业人口就有多少产能
- 熟练度曲线**沿用产量那条** `0.6 + 0.4 × 熟练度/100`（`production.ts:57` / `sim_core.gd:336`），
  不引入第二套熟练度语义
- 基数取 2.5 的理由：新工坊默认熟练度 50 时曲线值为 0.8，`2.5 × 0.8 = 2.0` 精确对上"一人顶两人"

## 三、工时需求

| 类别 | 建筑 | 建造力 |
|---|---|---|
| **采集**（11） | 农场 / 伐木场 / 采石场 / 粘土坑 / 狩猎营地 / 渔场 | **12** |
| **加工 · 穷人级**（4） | 粗面粉磨坊、粗面包房、木柴坊、砖窑 | **12** |
| **加工 · 中产级**（10） | 精面粉磨坊、白面包房、粗织坊、粗布衣坊、细织坊、常服坊、陶器坊、熏鱼坊、肉干坊、**建筑工坊** | **24** |
| **加工 · 富人级**（6） | 糕点房、**糖坊**、瓷窑、家政工坊、华服坊、皮衣坊 | **36** |
| **大型**（1） | 剧院 | **48** |
| **住房** | 茅屋 / 木屋 / 砖房 | **12 / 24 / 36** |
| **升级** | 每 +1 级 | **24 × 当前等级** |

分级规则：**该建筑产出最终被哪个（最低）阶层消费**（含缺货替代链）。
「建筑工坊」的产出是建造力本身、不属于任何阶层，按**中等规模**归 24。

**12 人（开局）的工期**：采集 1.0 天 / 加工 2.0 天 / 大型 4.0 天。
对比现状（所有东西固定 2 天、且**全部并行**）：便宜的快了、大件慢了、**多建要排队**。

## 四、队列

**建造与升级共用一条先进先出队列。**

```
黎明（06:00，用工分配之后）：
    constructionRateToday = 当日产能（**全天不变**，见 docs/spec.md §9.3）
    当日累计投入清零

每个工作小时（06:00–18:00，每小时一次）：
    rate = constructionRateToday ÷ 工作小时数      （常数，不每小时现算）
    从队首依次投入：
        工程.remaining -= rate      （用 r4 累积；r2 会在 12 次之后漂移）
        remaining <= 0 → 完工，溢出部分继续投给下一个
        产能耗尽 → 停止
夜晚（18:00）：
    诊断队首为什么没动（「等待材料」每天最多一条）
    把当日累计投入折成建造工资（markConstructionWorkers）
```

- **当天的量在黎明钉死**：白天只读 `constructionRateToday`，中途的人事变动
  动摇不了今天的每小时量（门槛：`construction_test.gd` 的 D 段）
- **开工时刻 = 这一天第一个工作小时**（材料在这一刻扣，不再等到入夜）
- 「开工」日志只在 `started` 翻转时写一次；「等待材料」写在夜晚，每天最多一条
  （逐小时写会刷 12 条屏）
- 只有**日总量**与从前一致（= 当日产能）；中间过程看得见

## 五、工资

```
建筑工坊工人            100%  （固定工位、熟练度高）
失业人口 · 在工地上      80%  （临时工、非熟练）
失业人口 · 没工程可做      0%  （取消保障金）
```

⚠️ **这一条等于取消现有的失业保障金**（`economy.welfareRate` 作废）。
后果需要一并处理：

- `population` / `satisfaction` 里对"失业"的处理要重看 —— 收入为 0 会拉低工资满意度
- 无工程时全村失业人口收入归零，可能引发饥饿与迁出
- `README.md` 与 `docs/content.md` 里"失业保障：领取保障金（可温饱）"的描述要删
- 政府支出结构变化：保障金科目消失，新增建造工资科目

## 六、材料：开工时扣，不是下单时扣

```
下单  → 只检查材料是否够，占住队列位，**不扣**
开工  → 扣材料（木材 / 石块 / 粘土 / 砖）
        开工 = 这一天第一个工作小时；材料不足 → 停在队首等待，不跳过
        夜晚补一条诊断「等待材料」（每天最多一条，不逐小时刷屏）
```

好处：排队 20 天不会把材料压死，仍可周转。

## 十、分两步实现

**第一步**：产能（仅失业人口部分）+ 队列 + 开工扣材料 + 升级排队 + 建造工资三段结构。
建筑工坊暂时按"普通失业人口"计（即不享受 2.5 × 熟练度加成）。

→ 这一步就能让"人多盖得快、多建要排队"跑起来，且平衡数字容易验证。

**第二步**：接上建筑工坊的 `2.5 × (0.6 + 0.4 × 熟练度/100)`，并把熟练度成长接进建造力。

每步都单独对拍验证，出问题好定位。

## 十一、实现时踩到的两个硬约束

这两条不是设计选择，是这套模型**必然**导出的结构性事实，改 AI / 调平衡时必须知道：

### 1. 建造力归零 = 永久死锁，建筑工坊必须是第一座

产能 = 失业人口 + 建筑工坊工人。一个**全员就业且没有工坊**的村子产能恰好为 0，
于是既建不出工坊、也建不出任何东西 —— 死锁。

- 开局那批失业人口（v0.3 是 12 人）是唯一的起手资本，**必须优先拿去建建筑工坊**，
  而不是被食品链一次吃光（食物链满员正好要 14 人 > 12 人）。
- 基线 AI 因此把建筑工坊排在所有建筑之前（`src/ai/heuristic.ts` 第 0 步）。

### 2. 不能靠「压低开岗数」来给工地留人

迁入闸门是 `admit = min(arrivals, allowance, 住房容量−人口, **岗位数−人口**)`，
而「岗位数」= `Σ shop.targetWorkers`（`population.ts`）。一旦为了留建造队而压低
`targetWorkers`，岗位数就低于人口 → **一个移民也进不来** → 村子上限被锁死。

所以建造力**只能**靠建筑工坊（固定工位）提供，不能靠"少开几个岗"。基线 AI 全程满员开岗。

### 3. 施工是串行队列，下单必须限流（AI 侧）

旧模型下施工并行、固定 2 天，AI 每天下一个单也无所谓。串行队列下同样的行为会让
队列无限增长（队尾永远轮不到），所以基线 AI 加了 `MAX_CONSTRUCTION_QUEUE = 4`。

### 4. v0.3 的开局必须"工坊优先"

v0.3 默认开局是 12 人、无建筑：食物链满员要 14 人 > 12 人，所以那 12 个失业人口是唯一
起手资本。先建食品链就会把人力一次吃光，产能归零；先建建筑工坊才能持续施工。
基线 AI 因此把建筑工坊排在第 0 步（`src/ai/heuristic.ts`）。
v1.0 开局自带一座建筑工坊，没有这个问题。

## 十二、队列是可管理的：调序与撤单（2026-10 实装）

队列以前只能"排"，玩家**没法改顺序**，排错了只能认。现在城镇中心多了一个
「建造队列」页签（`docs/town.md` §十五），后端两条动作（契约见 `docs/spec.md` §9.8）：

| 动作 | 语义 |
|---|---|
| `move_construction {id, delta}` | 把这条按 `delta` 的方向挪**一位**（-1 上移 / +1 下移） |
| `cancel_construction {id}` | 把这条从队列里撤掉，**退回还没干完的那份材料** |

### 12.1 调序只改"谁先吃到建造力"

队首先开工、产能没用完才溢给下一条 —— 所以顺序就是唯一有意义的操作对象。

- **不重算 `remaining`、不改 `started`、不退料**。已经在建的工程被挪到后面时，
  它只是**暂停**（前面的工程先吃产能），已经投进去的那部分一点不丢。
- 边界一律**拒绝**而不是静默夹取：队首再上移 → `已经是队首`；队尾再下移 →
  `已经是队尾`；`delta = 0` → `没有移动`；id 不在队列里 → `该工程已不在队列里`。

### 12.2 撤单的退料口径（关键：材料是**开工那一刻**才扣的）

这条口径不是"拍脑袋"，是 §六的直接推论：

```
还没开工  → 一分钱都没扣过 → 退 0（材料原封不动，谈不上"退回"）
已开工    → 退回量 = 已扣材料 × (remaining / totalRequired)
```

即"**只退还没干完的那一份**"：已经投进去的建造力对应的人工/料拿不回来。
建造力**本身**不退 —— 它是每日产能，不是库存（与 `demolish` 同口径）。

- 无实物材料的建筑按 `moneyCostBuild` / `moneyCostExpand` 扣过钱 → 金钱同比例退。
- 撤单会写一条**公告**（`取消「瓷窑」（已投入 28%），退回 木材×4.33、石块×2.17`）：
  它是唯一"扣了又还"的动作，退料明细没有别的出口。
- 撤单同时**放回土地名额**（`usedSlots` 把在建算作占用），表现层还要收掉地图上那处
  工地精灵（`world_view._prune_orphan_sites()`）—— 不收就是个永远不完工的"鬼工地"，
  地格也永远占着。
- 面板点 `×` 是**两步**（和"拆除"同一套）：第一下只亮出"会退回什么"
  （走 `construction_refund_preview()`，**只算不改**），第二下才真的撤。
  `remaining <= 0`（已完工、等次日黎明启用）的那条**不能撤** —— 它退 0，
  不想要应该等建成后走「拆除」。
