# 科技树设计（研究力与解锁）

> 状态：**已实装**（TS + Godot 双边）。
> TS：`src/engine/systems/research.ts` / `tools.ts` / `investment.ts` / `labor.ts`；
> GDScript：`godot/scripts/sim/sim_core.gd`；
> 公式契约已写进 `docs/spec.md` §10（研究）与 §11（工具）；
> 科技面板：`godot/scripts/ui/panel_tech.gd`（顶栏「科技」按钮）。
>
> 一句话：**商品与建筑要一项项研究出来；研究消耗原材料 + 科研力；科研力由「研究所」提供。**

---

## 一、设计目标

1. **开局只有最基础的食物链**：穷人能吃饱（粗面包 + 蔬菜），有木材盖房子，有茅屋住。其余全靠研究。
2. **研究花"原材料 + 科研力"**，不花金币：
   - 原材料给**产业链压力**——所有研究材料都必须来自**已解锁**的产业链（§1.1），
     于是"先能生产、才谈得上研究"。
   - 科研力给**人口与建筑压力**——研究所要占人、要发工资、要扩产。研究快慢由**你投了多少研究所**决定。
3. **科研力是与建造力同构的"每日产能"**：不进库存、当天不用完即作废、一条先进先出队列。
   玩家已经懂建造力，就不用再学第二套语义。
4. **研究所开局即可建，不需要研究**（2026-10 改）：原来用"一点基础科研力兜底 + 一项解锁自己的科技"
   来绕开"要研究所才能研究研究所"的死锁，现在直接把研究所做成默认建筑，
   并把 `research.baseRate` 归零 —— **研究所是科研力的唯一来源**，不存在死锁（建得起就行）。
5. **不打断现有经济**：不新增阶层、不改需求表、不改施工公式。科技只新增一件事——决定"能建什么"。
6. **配套加一条工具产业链**（§八）：工具坊用木材 + 石块造**石制工具**，工坊按工位消耗工具，
   换来**产出 ×1.25、投入不变**（"虚空产量"，灵感来自《戴森球计划》增产剂）。
   它是本设计里唯一的"生产力型"内容，也因此是最需要调平衡的一环。

### 1.1 唯一硬规则：科技只花"已解锁"的原料

> **每一项科技消耗的每一种原材料，都必须由它自己或其前置（含传递前置）解锁的建筑产出，
> 或是开局免费的产出（木材）。**

这条规则让依赖图**自动闭合**：玩家不可能遇到"要研究 X 却要先有 X 的产物"的死锁。
本文所有花费都按这条规则核对过（§四给了依赖图，可逐条验证）。

## 二、机制

### 2.1 科研力（与建造力同构）

```
每日科研力 = Σ(研究所在岗工人 × perWorker × (1 + levelBonus × (等级−1)) × (0.6 + 0.4 × 熟练度/100))
           （+ economy.research.baseRate，**现在恒为 0** —— 见下）

一个科技需要「n 科研力」= n 个人·天
工期 = 需求量 ÷ 每日科研力（产能逐日投入，不用完就浪费）
多个科技 → 一条先进先出队列，串行
```

- **不进库存、不结转**——和建造力完全一致（`docs/construction.md` §一）。
- 熟练度曲线**沿用产量那条** `0.6 + 0.4 × 熟练度/100`，不引入第二套语义。
- **基础科研力**：`economy.research.baseRate`，**2026-10 起为 0**。
  原来是 2.0/天（"村长 + 几个识字村民的土办法"，慢到必须建研究所），
  但那样"建了研究所才解锁研究"就成了一句空话 —— 归零之后语义才干净：
  **没有研究所 = 完全不能研究**。开局木材 ≥ 12 就建得起研究所，所以不会死锁。

| 来源 | 每日科研力 |
|---|---|
| 村庄基础 | **2.0**（固定） |
| 研究所 · 1 级（6 工位） | 每人 **3.0** × 熟练度曲线 |
| 研究所 · 2 级（9 工位） | 每人 **3.9**（+30%） |
| 研究所 · 3 级（12 工位） | 每人 **4.8**（+60%） |

满员（熟练度 50 → 曲线 0.8）时一座研究所的日产能：

| 等级 | 工位 | 每人 | 满员日产 |
|---|---|---|---|
| 1 | 6 | 3.0 | **14.4** |
| 2 | 9 | 3.9 | **28.1** |
| 3 | 12 | 4.8 | **46.1** |

> 熟练度满 100 时曲线为 1.0，所以长期看每座研究所还能再涨 25%。

### 2.2 研究所（新建筑）

```jsonc
{
  "id": "research_institute",
  "nameZh": "研究所",
  "tier": 3,
  "workers": 6,              // 参照满员 = 1 级工位上限
  "maxWorkers": 6,
  "buildCost": { "wood": 12 },
  "buildWork": 24,
  "capacity": {
    "kind": "research",
    "perWorker": 3.0,        // 每在岗工人的基础科研力（再乘熟练度曲线）
    "levelBonus": 0.3,       // 每升 1 级 +30% 科研力
    "slotsPerLevel": 3       // 每升 1 级 +3 工位
  }
}
```

- **没有 `recipe`**：它产出的是科研力（产能），不是商品——与建筑工坊同类。
- **升级**（`expand`，现有规则）：材料成本 × 当前等级；建造力 `24 × 当前等级`。
  **升级同时给两样东西**：更多工位（+3/级）+ 每人工科研力加成（+30%/级）。所以升级是**乘性收益**。
- `buildCost` 只有木材：研究所是**第一项科技**，此时除木材外什么都还没解锁（满足 §1.1）。
- 外观：需要一个明显的"学术/塔楼"造型，待定（`art`）。

### 2.3 状态

```ts
interface ResearchProject {
  id: TechID
  remaining: number      // 还差的科研力
  totalRequired: number  // 总需求（进度条用）
  started: boolean       // 材料是否已扣（开工时扣）
}

// GameState 新增：
research: {
  done: TechID[]
  queue: ResearchProject[]   // 先进先出；产能从队首开始投
}
```

> 结构与 `Construction` **刻意保持一致**（`remaining` / `totalRequired` / `started`），
> 两边可以共用同一套进度条与队列 UI，也便于对照审查。

### 2.4 动作

| 动作 | 说明 |
|---|---|
| `research { techId }` | 入队。只检查资源够不够，**不扣材料**（开工时扣）。前置未满足 / 已研究 / 已排队 → `ok:false` 带原因 |
| `cancel_research { techId }` | 从队列移除。**已扣的材料不退**（与施工一致） |

### 2.5 每日结算

**节奏与施工完全一致**：科研力是"当天的产能"，摊在白天的工作小时里逐小时投入
（每小时 `rate / 工作小时数`，是个**常数**）；夜晚只做诊断收尾。

> 施工那边钉的是同一道闸（`planConstructionDay` → `constructionRateToday`，
> 见 `docs/spec.md` §9.3）：两边的"当天总量"都不依赖"同一天里速率恰好不变"。

```
黎明 planResearchDay(state)：                # 排在 assignLabor 之后、第一个工作小时之前
    researchRateToday = researchRate(state)  # §2.1；当天预算，全天不变（"一天总量"的硬闸）
    researchWorkToday = 0

白天 applyResearchHours(state, fraction)：   # workStart <= h < workEnd，每小时一次
    left = min(researchRateToday × fraction, researchRateToday − researchWorkToday)
    for p in research.queue:                 # 队首 → 队尾
        if left <= 0: break
        if not p.started:
            材料不足 → 记「等待材料」（p.waiting 去重，每天最多一条）; break  # 停在队首，不跳过
            足够   → 扣材料; p.started = true; 记「开始研究」
        used = min(left, p.remaining)
        p.remaining = max(0, round4(p.remaining − used))    # r4：12 次 r2 会漂移
        left = round4(left − used)
        researchWorkToday = round4(researchWorkToday + used)

夜晚 settleResearch(state, day)：            # 排在 settleConstruction 之后
    # 产能已经投完了，这里只诊断"队首为什么没动"（每天最多一条）
    若 researchRate > 0 且 queue[0] 该动没动且材料不足 → 记「等待材料」

黎明 activateResearch(state, day)：          # 与施工一致：昨晚跑完、今晨生效
    while queue 非空 and queue[0].remaining <= 0:
        done.push(queue.shift().id)
        记日志「研究完成：<名称>」
```

- **每小时的量是常数**（不是"把队首剩下的需求摊到当天剩下的小时里"）：队首只剩 5、
  日产能 12 时，就是每小时 1、走 5 个小时在**当天中途**跑完。
- **队首中途跑完 → 那一格剩下的产能继续投给下一条**（同格、串行）：剩余产能不许丢，
  这是"一天总量 = 当天科研力"的关键；队列空了就作废（**不结转第二天**）。
- **完工不提前启用**：跑完的科技仍留在队列里，等次日黎明 `activateResearch` 才出队生效。
- **施工与科研完全同构**：两边都在黎明钉住当日预算（`planConstructionDay` /
  `planResearchDay`），白天只按"钉住的预算 ÷ 工作小时数"投入 —— 当天中途的人事变动
  （在岗人数 / 失业人口）动摇不了当天总量，也不依赖"同一天里速率恰好不变"这个隐含前提。

与施工的对照：

| | 施工（`docs/construction.md`） | 研究 |
|---|---|---|
| 产能来源 | 失业人口 + 建筑工坊工人 | 基础科研力 + 研究所工人 |
| 计量单位 | 建造力（人·天） | 科研力（人·天） |
| 每日预算 | 黎明那一刻的 `constructionRate`（`constructionRateToday`） | 黎明那一刻的 `researchRate`（`researchRateToday`） |
| 材料 | 开工时扣（当天第一个工作小时） | 开工时扣（同） |
| 队列 | 先进先出，共用一条 | 先进先出，**独立一条** |
| 中途跑完 | 同格溢给下一条 | 同格溢给下一条（同） |
| 完成后 | 次日黎明启用建筑 | 次日黎明解锁科技 |
| 不结转 | ✅ | ✅ |

**两条队列互不争抢**：研究所的工人是**在岗就业**，因此不计入「失业人口」，
不会同时给建造力供能——不会一笔人力被算两次。但它们**会和其他工坊抢人口**，这是真实取舍。

### 2.6 解锁判定

```
buildingAvailable(defId) =
    not 任何科技 unlocks 该建筑        # 开局免费的那批
 or 该建筑所属科技 ∈ research.done
```

- 每座建筑**至多被一项科技解锁**（数据校验强制，见 §6.1）。
- **产品不单独设锁**：商品的可用性由"产出它的建筑是否解锁"决定
  （本文「解锁产品」列只是给玩家看的推导结果，不写进数据，避免两处真相）。
- 阶层需求表**不改**：某个商品没解锁，该需求就落在缺货替代链上（`fallbacks`），
  代价是满意度下降——这正是"该研究却不研究"的压力。

### 2.7 UI

- 建造栏（`build_bar.gd`）：**未解锁的建筑仍显示**，灰底 + 锁图标，
  tooltip 写「需要科技：营造（未研究）」。不要隐藏——玩家需要知道有什么可追求。
- 新增**科技面板**：按纪元分组；每项显示 名称 / 科研力需求 / 花费材料 / 前置 / 解锁建筑与产品；
  可研究 / 研究中（剩余科研力 + 预计天数）/ 已完成 三态；顶栏加「科技」按钮。
- 顶栏信息行加「科研力 14.4/天」，与已有的「建造力 12/天」并列。
- 科技面板顶部显示产能构成：「研究所 ×2（1 级）= 28.8/天」，
  让"该扩建研究所了"一眼可见；没有研究所时显示「0/天 —— 先建研究所」。

### 2.8 基线 AI

- **研究**：固定的优先级表（= §四依赖图的拓扑序）。每天：若队列为空 → 取优先级最高、
  前置已满足、材料买得起的科技下单。
- **研究所**：把「至少一座研究所」纳入建造优先级（排在建筑工坊之后、食品链之前还是之后需要实测），
  并在「研究队列长期非空」时扩建/升级研究所。
- **工具坊**：研究出石制工具后建 1 座工具坊；当「生产工位数 ÷ 40」> 已有工具坊数时再建。
  工具是耗材，必须持续生产——AI 要把它当**常驻产线**而不是一次性投资。

> ⚠️ **2026-10 变更**：原来的第 1 项 `research_institute`（研究所）**已删除**。
> 研究所改成**开局即可建**的普通建筑（不需要任何科技），
> 并且 `economy.research.baseRate` 从 2.0 归零 —— **研究所变成科研力的唯一来源**：
> 没有研究所 = 完全不能研究。见 `docs/town.md` §6。
> 于是纪元 1 从 6 项变 5 项、总科研力 1552 → 1540。
>
> ⚠️ **2026-10 再变更**：第 28 项 **`housing_works`（住房坊）已删除** ——
> 它把 `wood`+`brick` 做成 `hut`「商品」，但没有任何消费者：
> 建房走的是 `build_housing` 动作（消耗 `housing.json` 的 `buildCost`），居民需求与
> 其它配方都不吃 `hut`。也就是说花 120 科研力 + 80 木 + 40 砖解锁的是一座**纯亏损**建筑。
> 于是 43 → **42 项**、2,340 → **2,220 科研力**，产业建筑 37 → **36 座**，
> 商品 36 → **33 种**（`hut` / `wooden_house` / `brick_house` 的"商品"身份一并撤掉；
> 它们**作为住房**照旧，见 `content/housing.json` 与 §二）。

- `科研力` = 完成所需的人·天。**没有金币成本**。
- `花费` 是仓库里的实物原料（开工时扣）。
- `前置` 是**知识前置**（成本材料来自哪些科技，见 §1.1 规则，两者可能不同）。

### 效率科技（15 项，横跨纪元 2/3/4）

前 27 项都是"解锁"型（解锁建筑/住房）。另有一类是**效率型**：不解锁任何东西，
只给一个**加成**。它们按"每类三级"排，级别分别落在**纪元 2 / 3 / 4**，
加成 **+20% / +35% / +50%**。

| 类别 | 一级（era2，30） | 二级（era3，50） | 三级（era4，80） | 效果 |
|---|---|---|---|---|
| 农业食品 | **轮作** `crop_rotation` | **灌溉** `irrigation` | **良种** `improved_seeds` | 所有 `sector=agri` 的建筑产出 +20/+35/+50% |
| 工业商品 | **作坊分工** `workshop_division` | **标准化** `standardization` | **流水线** `assembly_line` | 所有 `sector=goods` 的建筑产出 +20/+35/+50% |
| 建材 | **窑炉改良** `kiln_upgrade` | **木工机械** `sawmill_machinery` | **制砖机械** `brick_press` | 所有 `sector=material` 的建筑产出 +20/+35/+50% |
| 研究速度 | **抄书房** `scriptorium` | **学院** `academy` | **印刷术** `printing_press` | 每日科研力 +20/+35/+50% |
| 建造速度 | **起重架** `crane` | **脚手架** `scaffolding` | **预制件** `prefab_parts` | 每日建造力 +20/+35/+50% |

- **加法叠加**：三级全拿 = 该类别 **+105%**（不是 1.2×1.35×1.5 = 2.43 那种连乘）。
  理由：连乘后期滚雪球，而且玩家在面板上没法一眼算出"我现在是多少"。
- **与工具相乘**：产出那条路上的倍率 = `toolBoost`（石制工具 +25%）**×** 产业加成。
  两条独立路线，都拿满 = 1.25 × 2.05。
- **前置**：同级之间互相独立（五条链并行）；五个 **L1 都挂 `stonework`**，
  之后每一级只要求同级的前一级（如 `irrigation` ← `crop_rotation`）。
  - 为什么 L1 要挂 `stonework`：L2 起要花**石块**，而"前置闭包里原料必须可达"
    是 `validate.ts` §1.1 的硬闸门。速度树这条链什么都不解锁、闭包恒空 → 石头永远不可达。
    挂上 `stonework`（它解锁采石场）之后，石头顺着链被 L2/L3 继承。
    **这是改内容，而不是给效率科技开后门** —— 闸门对所有科技一视同仁。
- 花费：era2 = 木材 20（建材那条木材 20 + 石块 20）；era3 = 木材 30 + 石块 15；era4 = 木材 40 + 石块 25。
  - L3 **不放砖**：砖要靠 `brickmaking` 那条线，跟速度树无关，硬挂上去只会让树更绕。
- `unlocks` 一律为空 —— 校验器允许**"解锁或效果至少给一个"**（见 §6.1）。
- 归类靠建筑上的 `sector` 字段（`agri`/`goods`/`material`，32 座有配方的建筑各属一类）。
  **为什么不复用商品的 `category`**：`wheat` 和 `stone` 都叫 `raw`，靠商品类别分不出
  "农业原料"和"建材"。
- 引擎口径写在 `docs/spec.md`（产出 / 科研 / 建造三处乘法，以及 `effects` 的聚合方式）。
- UI：科技面板顶部会显示**当前累计加成**，每张卡片的 tooltip 里也有这一项的效果。

**加这 15 项之后的总量：42 项科技 / 5 个纪元 / 2,220 科研力。**

### 民生服务科技（3 项，横跨纪元 3/4/5 —— 2026-10 追加）

用户："新增，增加（治安、教育、医疗）的科技（三个一起加）培训、民生工程、治理三级"。

### 6.2 建筑的 `capacity` 字段（顺带统一建筑工坊）

现在有**两种**"不产商品、只产产能"的建筑（建筑工坊 / 研究所），需要一个数据字段来区分，
不能再靠"没有 recipe"隐式判断。建议加：

```jsonc
// 研究所
"capacity": { "kind": "research", "perWorker": 3.0, "levelBonus": 0.3, "slotsPerLevel": 3 }

// 建筑工坊（把现在写死在 economy.json 的 workshopBase 挪进来）
"capacity": { "kind": "build", "perWorker": 2.5, "levelBonus": 0, "slotsPerLevel": 0 }
```

- `kind` 决定这份产能喂给哪条队列（建造力 / 科研力）。
- `perWorker` 乘熟练度曲线（沿用 `skillEffectBase/Slope`）。
- `levelBonus` × (等级−1) 是**升级的乘性收益**；`slotsPerLevel` × (等级−1) 加在 `maxWorkers` 上。
- 建筑工坊取 `levelBonus: 0`，**行为与现在完全一致**（升级只加产出不受益），不会改变 golden。

> **替代方案**（不想动已实装的建造力代码）：`kind` 只在研究所上用，建筑工坊继续读
> `economy.construction.workshopBase`，并用 id 判断是不是建筑工坊。
> 本文推荐统一——改动只有几行，但从此产能来源完全数据驱动，加第三种产能不用再改引擎。

`assignLabor` 里工位上限要跟着等级走：

```ts
const slots = def.maxWorkers + (capacity?.slotsPerLevel ?? 0) * (shop.level - 1)
want = max(0, min(shop.targetWorkers, slots))
```

## 七、数值初值与平衡风险

**这些数字是设计初值，不是调好的值。** 实装后必须用 `npm run sim` 跑 100/200 天校准。

### 7.1 相比"金币 + 天数"版，财政风险已解除

上一版设计让研究花金币（全树约 ¥7,990），而 v0.3 基线 100 天政府余额是 `2000 → -1413`，
本身在亏钱——那版会卡在纪元 3 前后。

改成"材料 + 科研力"后，**研究不再直接消耗金币**，这条死路没了。新的成本结构是：

| 成本 | 性质 | 会不会卡死 |
|---|---|---|
| 原材料 | 实物，来自已解锁产业链 | 不会死锁（§1.1 保证），但会与生产/施工**争原料** |
| 科研力 | 研究所工人 × 时间 | 不会死锁（有 2.0/天基础兜底） |
| 研究所工资 | **金币，持续支出** | ⚠️ 这是把财政风险换了个形式 |

**新的平衡焦点**：研究所工人是**在岗就业**，要走 `payWages` 发工资。
一座满员 1 级研究所 6 人，按 `refWage 3` 计约 **¥18/天**（含技能加成更高）。
3 座 3 级研究所 36 人 ≈ **¥108/天**——这才是财政压力所在。
好处是它**可调、可停**（把人撤下来就不花钱），比"一次性 ¥7,990"健康得多。

### 7.2 需要实测的三件事

1. ~~**基础科研力 2.0 是否合适**~~ **已拍板（2026-10）**：归零，研究所是唯一来源
   —— 见 §一 原则 4。于是"研究所该建几座"变成纯取舍问题（下面的第 2 条）。
2. **研究所该建几座**：人口是有限的，研究所吃掉的 6/9/12 人本可以去产商品。
   如果 AI 发现"多建研究所永远划算"，说明科研力定价太便宜，应下调 `perWorker` 或上调需求。
3. **木材瓶颈**：研究所本体、升级、工具坊、以及几乎每项研究的材料都含木材。
   伐木场的工位上限现在是 **6**（与农田同档，见 `docs/content.md` §用工上限），
   所以木材不够时的正解是**多建一座伐木场**，不是把 100 个人塞进一座。
4. **工具是否无脑碾压**：见 §8.4 —— 尤其是"采集业零投入却吃 +25%"这一点，
   可能让"先给采集业装工具"成为唯一最优解。

### 7.3 次要风险

- **中产自动出现而科技跟不上**：中产由存款 ≥ 40 自动触发，与科技无关。
  研究太慢会出现"一批中产住茅屋扣满意度"的难堪期。纪元 3 的需求量（50）是最可能要下调的。
- **`制陶` / `制瓷` / `烧砖` 三者争粘土**：跨纪元 2 与 4，粘土坑可能需要更早扩产。
- ~~**研究所无配方 ⇒ 建造栏分类**~~ **已实装（2026-10）**：新增了「**市政**」页签
  （`build_bar.gd` 的 `CIVIC` 白名单），把**仓库 / 建筑工坊 / 研究所**这三座没有
  `recipe` 的服务建筑从「工业」里挪出来 —— 它们跟工坊不是一类东西。
  用户点名："建筑菜单加一个 tab 是市政，把仓库/建造中心/研究中心放进去"。
  ⚠️ 2026-10 又加了一座 **贸易市场**（同样没有 `recipe`）：它原来按 arch 推导掉进
  「工业」页，而工业页有 14 张卡、要翻页，它就藏在第 2 页最后一格 —— 用户的原话是
  "市场这个建筑没了"。现在它在市政页（4 张卡，一眼看得见），见 `docs/town.md` §二十五。
- **「工业」拆成两页（2026-10）**：用户："工业的建筑太多了，把民生工业（衣服、陶器、瓷器）
  和重工业（建材，冶炼之类）分成两个 tab"。现在建造栏 11 个 tab，`ContentDB.build_category()`
  先查两张白名单：
  | 页 | 名单 | 内容 |
  |---|---|---|
  | 「民生工业」 | `CAT_CONSUMER` | 粗织坊 / 细织坊 / 粗布衣坊 / 常服坊 / 华服坊 / 皮衣坊 / 陶器坊 / 瓷窑（8 座）|
  | 「重工业」 | `CAT_HEAVY` | 冶炼场 / 木柴坊 / 砖窑 / 石制工具作坊 / 铁制工具作坊（5 座）|

  工具作坊跟建材走，不跟衣服走 —— 它们产的是**其它建筑的上游**（工具），不是消费品。
  「工业」这个分类名已不存在；`build_category()` 的兜底也改成「民生工业」（新的消费类工坊
  自动落这里，建材/冶炼类记得点名进 `CAT_HEAVY`）。
  ⚠️ 分类名和 `build_bar.TABS` 必须逐字对上，否则那几座建筑会在建造栏里**静默消失** ——
  门槛 `bartab` 现在会遍历内容包里每一座建筑，分类落不到任何 Tab 就红。

## 八、配套内容：工具产业链（2026-10 已实装）

> ✅ 本节**已实装**：商品 `stone_tools`、建筑 `tool_works`、机制公式在 `docs/spec.md` §11.1 / §11.2。
> 2026-10 用户补了一句「一个工人 10 天消耗 1 工具」→ `perWorkstation` **0.05 → 0.1**（见 §8.3）。

### 8.1 商品：石制工具

```jsonc
// content/goods.json —— 新增 category "tool"
{ "id": "stone_tools", "nameZh": "石制工具", "tier": 1, "category": "tool",
  "storable": true, "baseValue": 4.0, "toolBonus": 0.25 }
```

- **不是消费品**：任何阶层都没有工具需求，所以它不参与居民购买，只走**工业消耗**
  （`ledgerToday.consumed`，与 `recipe.inputs` 同一本账）。
- `toolBonus` 是**这个工具品级**的产出加成，写在商品上而不是写在引擎里 —— 为了将来的分级（§8.5）。
- 新增 `category: "tool"`：`GoodCategory` 联合类型与 `validate.ts` 的 `CATEGORIES` 都要加。
  工具**不是奢侈品**（`isLuxuryGood` 读的是 `luxury` 标志，工具不设该标志）。

### 8.2 建筑：工具坊

```jsonc
// content/buildings.json
{
  "id": "tool_works", "nameZh": "工具坊",
  "tier": 2, "workers": 3, "maxWorkers": 6,
  "buildCost": { "wood": 6, "stone": 3 },          // tier 2 标准成本
  "recipe": { "inputs": { "wood": 5, "stone": 5 }, "output": { "stone_tools": 2 }, "baseRate": 1 },
  "buildWork": 24                                  // 中产级加工
}
```

满员（3 人）产 **2 石制工具/天**，日耗 **5 木材 + 5 石块**。

### 8.3 机制：工位耗材 + 成品加成

```jsonc
// content/economy.json
"tools": {
  "perWorkstation": 0.1,           // 每个在岗工位每日消耗的工具数（= 一个工人 10 天 1 件）
  "order": ["stone_tools"]         // 由低到高；将来加青铜/铁工具就往后排
}
```

**黎明（在 `planProduction` 排产之前分配，当天不再变）**

```
for shop in shops:
    if not (shop.active and def.recipe exists): continue     # 只有产商品的工坊
    workers = assignedWorkers(shop.id)                       # 在岗工人数 = 实际运转的工位
    if workers <= 0: continue
    for gid in reverse(economy.tools.order):                 # 从最高级工具往下找
        need = perWorkstation × workers
        if goods[gid] >= need:
            goods[gid] -= need
            ledgerToday.consumed[gid] += need
            shop.toolBoost = 1 + ALL_GOODS[gid].toolBonus     # 1.25
            break
    else:
        shop.toolBoost = 1.0                                  # 没工具 → 无加成
```

**生产小时（`production.ts` 的 `runProductionStep`，只改产出那两行）**

```
goods[g]           += q × batches × shop.toolBoost      # ← 唯一改动
ledgerToday.produced[g] += q × batches × shop.toolBoost

# 投入的两行**完全不动**：q × batches
```

**这条修改的全部效果就是"投入不变、产出 ×1.25"** —— 单位原料的成品率提高 25%，
多出来的 25% 是凭空出现的（"虚空产量"/合格率提升），正是《戴森球计划》增产剂的语义。

**几条必须明确的边界**

| 事项 | 结论 |
|---|---|
| 与熟练度叠加 | **乘性**：熟练度提升 `desired`（投入与产出一同变大），工具只放大产出。两者互不干扰 |
| 分配粒度 | **每天黎明一次性分配**，当天不变；跳过中间态，也让存档只需保存 `shop.toolBoost` |
| 工具不够时 | **按 `state.shops` 顺序**先到先得，耗尽后后面的工坊无加成（确定性，便于 golden 对拍）。
替代方案是按需等比分配，但那会让"我到底有没有加成"变得不直观 |
| 产能建筑 | **建筑工坊 / 研究所不耗工具**：它们不产商品，"1.25 倍成品"无从施加。
将来可扩展为"工具提高建造力 / 科研力" |
| 采集业（`inputs: {}`） | **照样吃加成**，且因为零投入，是**收益最高的目标**（详见 §8.4） |
| 与研究/施工的关系 | 工具只影响 `recipe.output`，所以**不改建造力、不改科研力、不改研究工时** |

### 8.4 数值与平衡

| 项 | 值 |
|---|---|
| 一座满员工具坊 | 3 人 → 2 工具/天 |
| 单工位日耗 | **按工具耐久**：石制 10 天 1 件（0.1）/ 铁制 15 天 1 件（0.0667）；科技"工具寿命"最高再 +50% |
| 一座工具坊能供养 | 2 ÷ 0.1 = **20 个在岗工位** |
| 20 工位的收益 | 20 × 1.25（石制）或 ×1.6（铁制）= 凭空多出 5 ~ 12 个工位的产能 |
| 代价 | 3 个人（本可去产商品）+ 5 木材 + 5 石块/天 |

**平衡判断：+25% 全局产出换 3 人 + 每天 5 木 5 石，明显划算，工具坊会成为"必建"。**
这本身可以接受（它就该是核心基建），但实装后必须确认它**不是无脑碾压**：

- 若发现"多建工具坊永远划算" → 下调 `toolBonus`（0.25 → 0.15）或上调 `perWorkstation`
- 若发现"没人愿意建" → 反向调
- **这两个数是本机制唯一的平衡旋钮**，其他都是设计给定（0.05 / 1.25）

⚠️ **最需要实测的一点**：采集业（农田 / 伐木场 / 采石场 / 粘土坑）的 `inputs` 是空的，
所以工具给它们的是"零成本 +25%"，收益最高。这会让"**先给采集业装工具**"成为最优解。
这可能正是想要的效果（农具改良），也可能需要限制（例如采集业不耗工具也不加成）。
**实装后要用 `npm run sim` 看清这一点再决定。**

### 8.4.1 工具耐久与"工具寿命"科技（2026-10 实装）

用户："铁制工具更耐用，15 天消耗一个，生产力加成提升"；"工具耐用可以做为科技，寿命延长 20%、50% 两档"。

- 消耗不再是一个全局速率，而是**每种工具按自己的耐久**：
  `每工人每日消耗 = 1 / (durabilityDays × (1 + 工具寿命加成))`
- 石制 `durabilityDays: 10`（= 原来的 0.1/人/日，行为不变）；铁制 `durabilityDays: 15`
- 铁制 `toolBonus: 0.6`（+60%），石制仍是 `0.25`
- 两项科技：**淬火** `tempering` +20%、**精炼** `refining` +50%
  - ⚠️ **取最高、不叠加**（用户 2026-10 定的）：都研究完是 +50%，不是 +70%。
    实现：`TechEffectKey` 加 `toolLife`，`tech_bonus.ts::MAX_KEYS` / GD `MAX_EFFECT_KEYS` 单独取 `max`
- 分配仍从 `economy.tools.order`（`["stone_tools", "iron_tools"]`）**从高级往低级找**
- 没有 `durabilityDays` 的老内容退回 `economy.tools.perWorkstation`（= 0.1，行为不变）

| 局面 | 石制有效天数 | 铁制有效天数 |
|---|---|---|
| 基础 | 10 | 15 |
| 淬火 | 12 | 18 |
| 精炼（或两档都有）| 15 | 22.5 |

## 十、研究队列可管理：调序与撤单（2026-10 实装）

> 用户："研究实际上也有一个队列，会按照队列来研究，**无法调整顺序**，需要有一个面板来调整。
> ……在**研究所**的面板加一个 tab，里面是研究队列，每一项左侧是缩略图，研究内容/效果，
> 已经使用的研究力/需要的研究力，然后右侧三个按钮：向上、向下、叉（取消研究，
> 未研究的已扣除的全额返还材料，已经开始研究按研究进度返还材料）。"

研究队列（`research.queue`）本来就是先进先出的一条：队首先吃到科研力、产能没用完才溢给
下一条（`docs/spec.md` §10.3）。所以"顺序"就是唯一能操作的东西。

| 动作 | 语义 | 契约 |
|---|---|---|
| `move_research {id, delta}` | 按方向挪**一位**，只改顺序（不重算进度、不动 `started`、不退料） | spec §10.7 |
| `cancel_research {techId}` | 从队列移除 + **按进度退回原料** | spec §10.7 |

**退料口径与施工的撤单完全一致**（原先写的"已扣材料不退"作废）：

```
还没开工 → 退 0                    # 原料是开工那一刻扣的，没开过工就一分没扣
已开工   → 已扣原料 × (remaining / totalRequired)
科研力本身不退                      # 它是每日产能，不是库存
```

**连带改掉的一处**：`activateResearch` 从"只看队首"改成**扫全队列**（与施工的
`activateCompleted` 同形制）—— 调序能把一条跑完的科技挪到后面，只认队首的话它会卡在
队列里，玩家看到"研究完成了却没解锁"。

**界面**：研究所的建筑面板多一个「研究队列」页签（共用控件 `queue_box.gd`，与城镇中心
的「建造队列」页、建筑工坊面板读的是同一份代码）：
缩略图 = 科技图标，名字 + 状态（`研究中` / `已完成（次日黎明生效）` / `排队中（前面还有 N 项）` /
`等待材料（缺 …）`），第二行是「已用 X / 需要 Y 科研力（Z%）」，第三行是**研究内容/效果**
（`效果 建材 +20%`、`解锁 采石场`）。撤单是两步（第一下亮出会退回什么）。

### 10.1 科技面板里的「研究队列」页签（2026-10 追加）

> 用户："我在科研面板里面点研究，还要到科研中心去找研究队列，很不方便，
> 应该研究队列是一个 tab，也可以挂进科研面板。"

`panel_tech.gd` 现在有**两个页签**：`科技树`（原来的树）与 `研究队列`（同一个 `QueueBox`，
`Kind.RESEARCH`）。两页互斥显示；队列页顶上一行提示"↑↓ 调序 · × 撤单；研究与调序当场生效"，

### 10.2 研究相关的三条命令**当场生效**（2026-10）

> 用户："我白天点了一个研究……结果队列里没有，没有实时出现。要到第二天才能调整顺序太蠢了。"
> "调顺序上下箭头没有反应，是不是没有实时生效？"

`research` / `cancel_research` / `move_research` 这三条**不再等黎明**：它们不花资源
（材料在**开工那一刻**才扣），只动一条队列。实现上是一份名单：

```
TS   `tick.ts::IMMEDIATE_ACTIONS`  + `queueActions()`（advanceHour/advanceDay 先应用它们）
GD   `sim_core.IMMEDIATE_ACTIONS`  + `enqueue()` / `tick_hour()` 分流
```

⚠️ 其余动作（建造 / 拆除 / 改价 / 招工 …）仍然**次日黎明生效** —— 那是"一天一结算"的核心口径，
也是黄金轨迹的确定性来源；门槛里留了一条反例断言（`check:queues`：建造动作必须留在 `pending`）。

**"科研力一天分配一次"是误解**：科研力是**按工作小时**投入队首的（每小时
`researchRateToday / 工作小时数`，队首跑完就在同一小时里溢给下一条，见 spec §10.3）。
所以调序当场生效 = **当天剩下的那几个小时改投给新队首**；已经投进去的部分当然留在原科技上。

门槛：`scripts/check-queues.ts`（当场进队列 / 当场调序 / 当场撤单 + 建造仍等黎明的反例）、
`godot/tools/tech_test.gd`（点卡片当场进队列、科技面板里有 `QueuePage`、点 ▲ 当场改顺序）、
`godot/tools/queue_test.gd`（研究队列调序 / 撤单同口径）。

门槛：`scripts/check-queues.ts` + `godot/tools/queue_test.gd`（同口径同数字）、
`godot/tools/inspector_test.gd`（页签名与三件套按钮）。
